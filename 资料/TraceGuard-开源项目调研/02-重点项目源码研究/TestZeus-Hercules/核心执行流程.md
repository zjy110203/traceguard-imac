## 1. Planner 如何生成执行计划（问题 1）

**入口**：`core/simple_hercules.py:549 _planner_node(self, state: AgentState) -> dict[str, Any]`

1. 计数：`turn = state.get("planner_turn", 0) + 1`；超过 `planner_max_chat_round`（默认 500，runner 构造时传入）→ 直接生成终止失败 JSON（`_planner_node:554-594`）。
2. 组装消息：`messages = list(state["messages"])`，若首条不是 `SystemMessage` 则前置 `SystemMessage(content=planner.system_message)`（`:598-601`）。
3. 调用 LLM：`await self._invoke_planner(planner, messages, state, turn, start)`（`_invoke_planner` 在 `:518-543`，内部 `_ainvoke_with_context_fallback`，处理 `TimeoutError`→`_planner_timeout_result`、其他异常→`_planner_failure_result`）。
4. Planner 的 system_message 由 `PlannerAgent.__init__`（`high_level_planner_agent.py:19-59`）构造：`Template(base_prompt).safe_substitute(basic_test_information=user_ltm)` + `_json_instruction` 前缀；`get_planner_prompt()`（`:338-357`）在启用移动时注入 `mobile` helper 枚举。
5. 解析：`parse_response(content)`（`utils/response_parser.py:143`）→ `parsed`。
6. **决策校验与纠错**：若 parsed 含 `_PLANNER_DECISION_KEYS=("plan","next_step","terminate","final_response","target_helper")`（`:104-105`）则 `_validate_planner_decision(parsed)`（`:467-507`）：校验 terminate∈{yes,no}、is_assert/is_passed 为 bool、target_helper 合法（`_HELPER_MAP` + not_applicable）、terminate=no 时 next_step 非空；失败则一次 `_corrective_planner_prompt` 重试（`:620-662`），仍失败→`_planner_failure_result` 判红。
7. 提取字段（`:675-686`）：`next_step`、`target_helper`（默认 "browser"）、`terminate`（支持 bool true 归一化）、`final_response`、`is_assert`、`assert_summary`、`is_passed`、`plan`。
8. **僵尸循环保护**（`:688-751`）：空 next_step 连续 3 次（`_PLANNER_STALL_LIMIT=3`）→ 终止；重复的 next_step 只警告不终止（如多次点击"下一页"是合法的）。
9. 更新 state 并返回（`:765-790`），含 token/cost/step_timings 累计。

**Planner 输出 JSON schema**（`high_level_planner_agent.py:71-72,177-198`）：
```json
{"plan":"...","next_step":"...","terminate":"no","final_response":"","is_assert":false,
 "assert_summary":"","is_passed":false,"target_helper":"browser"}
```
`target_helper` 允许值（`:187`）：`browser|api|sec|sql|time_keeper|agent|mcp|executor|Not_Applicable`（mobile 开启时追加 `mobile`，`:331-334`）。

**计划本质**：prompt 要求 Planner "Parse Steps file/Gherkin into detailed execution plans with clear validation steps"（`:82-90`）、每步聚焦 WHAT 而非 HOW（`:117-129`）、每步带 closure nudge 与验证（`:139-152`）、最终步必须含断言（`:302`）、全部步骤 `(Completed)` 时立即 terminate=yes（`:286-295`）。**计划是 LLM 自然语言 + 结构化字段，不是编译器产物。**

## 2. Executor 如何执行步骤（问题 2）

**入口**：`core/simple_hercules.py:1121 _executor_node(self, state: AgentState) -> dict[str, Any]`

1. 读取 `next_step`/`target_helper`；若 next_step 为空或 `not_applicable` → 直接返回（回 planner，`:1141-1154`）。
2. 路由：`agent_name = self._HELPER_MAP.get(target_helper, "browser_nav_agent")`（`:1156`）；nav_agent 不存在则回退 browser（`:1158-1164`）。
3. 构造 helper 任务：`await self._build_helper_task(next_step, target_helper, state)`（`:1168`，方法在 `:878-886`）；浏览器类会拼入 `current_url`（`_resolve_current_url`，`:871-877`）。
4. **执行 agent 循环**：`raw_helper_response = await self._run_nav_agent(nav_agent, helper_task, agent_name)`（`:1170`）。
5. 计费/统计：从 `self._nav_token_log` 切片累加 prompt/completion tokens 与 cost（`:1169-1182`）。
6. 可选 observer：`if observer_invariants_enabled(): self._poll_invariants_safely()`（`:1190-1191`）。
7. 把 helper 响应写回 planner 对话：`messages.append(HumanMessage(content=f"[{agent_name}]: {helper_response}"))`（`:1193-1195`）；成功响应（`_helper_response_succeeded`：含 `##TERMINATE TASK##` 且无 failure markers，`:135-149`）记录 `completed_step_signatures`。
8. 更新 current_url（browser/agent 类型取实时 URL，`:1202-1204`）、last_helper_response、timing；返回 state（`:1222-1241`）。
9. `_route_after_executor` **始终返回 "planner"**（`:1442-1444`）——executor 不自行判定完成，永远回 Planner 决策。

**`_run_nav_agent`（`:1243-1380`）细节**：
- 取 `nav_agent.tools/llm/system_message`（`:1249-1251`）；无 llm 返回 `[ERROR]`，无 tools 则裸 LLM 调用（`:1253-1271`）。
- `llm_with_tools = llm.bind_tools(tools)`（`:1274`）；`tool_map = {t.name: t}`（`:1292`）。
- `for _turn in range(self.nav_agent_number_of_rounds)`（默认 50，runner `browser_nav_max_chat_round=50`）：LLM 调用→若 content 含 `##TERMINATE TASK##` 退出→无 tool_calls 退出→逐个 tool_call 调 `_execute_tool_call`→构造 `ToolMessage`→若 `_requires_state_refresh` 则 break 并提示重读（`:1348-1370`）。
- 上下文超限时 `_compress_messages` 后重试（`:1302-1316`）；耗尽轮次返回 `[ERROR] max nav rounds ...`（`:1372-1380`）。

**工具执行 `_execute_tool_call`（`:933-967`）**：按 `tool_obj.coroutine`/`tool_obj.func`/`ainvoke`/`invoke` 多种 seam 调用，统一 `str()` 化并 `_truncate_tool_result`（20000 字符上限），异常→`[TOOL ERROR] ...`。

## 3. Assertion 如何判定执行结果（问题 3）

**三条路径并存，且主体不是独立 Agent**：

### 3.1 Planner 自报（默认路径）
Planner JSON 的 `is_assert`/`is_passed`/`assert_summary`（`high_level_planner_agent.py:184-186`）由 LLM 填写；`_assertion_node`（`simple_hercules.py:1386-1423`）直接信任它们作为终局 verdict。

### 3.2 确定性断言工具（API 默认注册 / UI opt-in，代码判定）
- **UI**：`core/tools/ui_assertions.py` `assert_ui(payload, mode, expected, count, scope, forbidden, must_contain, raw)`（`:320-329`），模式 `contains/absent/count_eq/no_placeholder`（`:75`），`_evaluate_assert_ui`（`:341-479`）逐条给 `PASSED/FAILED/ERROR`。防护：空负载→ERROR（`:354-360`）；`absent` 必须有 `must_contain` 正对照（`:404-413`）；去 URL/id/class 噪声（`:204-213`）；未解析 `${name}`→ERROR（`:246-266`）。`capture_ui_value`（`:482-592`）把页面值存进 `${name}` 变量。注册条件 `ENABLE_UI_ASSERTIONS`（`:607-626`），**默认关**（`ui_assertions.py:13-15`）。
- **API**：`core/tools/api_assertions.py` `assert_json_path(response_json, path, operator, expected)`（`:316-324`），12 个 operator（`:44-57`）；`_evaluate`（`:335-405`）插值/operator 名错位纠正/占位符检查→`_evaluate_with_operator`（`:420-591`）用 `find_json_path` 解析、逐 operator 判定；多值需每个匹配都满足（`:474-480,558-591`）；严格类型相等 + 文本回退带 note（`:167-186`）。注册给 `api_nav_agent`（`:301-315`）。API Agent prompt 明确要求"Never judge a response field correct or incorrect by reading it yourself. Call assert_json_path"（`api_nav_agent.py:59-62`）。
- 两者都通过 `_record()` 写 `assertion_logger`（`ui_assertions.py:269-290`、`api_assertions.py:266-289`），以 `assertion_subject`（payload sha1[:12]）标注，报告期可去重。

### 3.3 报告期账本覆盖 + observer + strict verdict
- `utils/junit_helper.py:366-389` verdict policy：默认 `is_passed` 真且（非断言场景）terminate≠no 即绿；`STRICT_VERDICT=true` 时需 terminate=yes 且 `is_passed is True` 才绿。
- `junit_helper.py:391-401`：若账本有 `FAILED`/`ERROR` 且场景自称 pass（`claimed_pass`）→ 覆盖为 Failure；`Assertions Total/Passed/Failed/Unresolved` 作为 property（`:425-430`）；**零断言的 pass 仅标记 `Assertions Missing`（`:431-434`），不判红**。
- `core/invariants.py:1-22`：BINDING（HTTP 5xx、uncaught 前端异常）→ 写账本 `FAILED`；`simple_hercules.py:1070-1115 _apply_invariant_failure` 图外强制 `is_passed=False`。
- `high_level_planner_agent.py:326-357` 的 prompt 层规则："NEVER set terminate yes on first response"、"Always delegate to a helper first"、"helper ##TERMINATE TASK## 视为该步完成"。

**结论（问题 8 明确回答）**：**源码中未发现独立的 Assertion Agent 角色。** 实际断言判定由 **Planner 在 JSON 中自报 `is_passed/is_assert/assert_summary`**，辅以**注册在导航 Agent 上的确定性 Python 工具**（`assert_ui` / `assert_json_path`，UI 默认关闭）和**报告期基于断言账本/observer 的覆盖**共同完成；LangGraph 中的 `assertion` 节点只是写终局 JSON 的非 LLM 状态节点（`simple_hercules.py:1382-1423` 注释 "trusts planner's is_assert/is_passed/assert_summary"）。

## 4. Agent 状态如何流转（问题 4）

**真正的状态机在 `core/simple_hercules.py`（不是 `core/memory/state_handler.py`）**：

- `AgentState(TypedDict, total=False)`（`:57-90`）：见 `整体架构分析.md` 第 5 节字段表。
- `_build_graph()`（`:1446-1463`）：
  ```python
  graph = StateGraph(AgentState)
  graph.add_node("planner", self._planner_node)
  graph.add_node("executor", self._executor_node)
  graph.add_node("assertion", self._assertion_node)
  graph.set_entry_point("planner")
  graph.add_conditional_edges("planner", self._route_after_planner, {"executor":..., "assertion":..., "end": END})
  graph.add_conditional_edges("executor", self._route_after_executor, {"planner":..., "assertion":...})
  graph.add_edge("assertion", END)
  return graph.compile()
  ```
- 路由：planner→executor（未终止且非 not_applicable）、planner→assertion（终止且 is_assert，或 strict_verdict&not_applicable，或 is_assert&not_applicable）、planner→end（终止且非断言）；executor→planner（恒定）；assertion→END。
- 驱动：`process_command`（`:1550-1665`）构造 initial state（`:1572-1594`，`messages=[HumanMessage(task)]`、`terminate="no"`、`target_helper="browser"`、各计数为 0）→ `await self._graph.ainvoke(initial, config={"recursion_limit":2000, "run_name":"hercules-agent", "metadata":{"stake_id":...}})`（`:1597-1604`）。
- 每次节点返回的是**增量 dict**，LangGraph 合并进 state（如 `_planner_node` 返回 `planner_turn/messages/plan/...`，`_executor_node` 返回 messages/completed_step_signatures/total_steps/...）。
- 状态机外的旁路：`process_command` 图结束后，若 `_invariant_binding` 非空 → `_apply_invariant_failure(final_state)` 改写 verdict（`:1606-1610`）；异常 → `_failed_graph_result`（`:1648-1664`）。

**`core/memory/state_handler.py` 的真实作用**（`:1-109`）：进程全局 `_state_string`/`_state_dict`（按 `get_default_test_id()` 键控），`@tool store_data`（browser/api/sql nav 可用）把文本追加进字符串，`store_run_data` 保留最近 2 条 deque，`clear_runtime_state()` 跨 suite 清空。**它不是 StateGraph**，只是 Agent 间的"便签本"。

## 5. 浏览器操作如何调用（问题 5）

1. **会话创建**：`BaseRunner.initialize()`（`runner.py:74-79`）在 `SKIP_BROWSER` 未设置时创建 `PlaywrightManager(gui_input_mode=False, stake_id=...)` 并 `await async_initialize()`；`async_initialize`（`playwright_manager.py:338-363`）建目录→`start_playwright()`（`playwright().start()`，`:372-374`）→`ensure_browser_context()`→`setup_handlers()`→`go_to_homepage()`（默认 `about:blank`，`:94`）。
2. **单例模型**：`PlaywrightManager.__new__`（`:119-140`）按 stake_id 缓存实例（`_instances`），无 stake_id 用默认实例（stake_id "0"）；因此工具函数里 `PlaywrightManager()` 拿到的是同一实例（如 `get_interactive_elements.py:218`、`click_using_selector.py:52`、`browser_assist_tools.py:32`）。
3. **工具取页**：`get_current_page()`（`playwright_manager.py:1097`）/ `get_current_url()`（`:1088`）；`click` 工具把 md 转成 `[md='N']`（`click_using_selector.py:44-53`），再 `perform_javascript_click`（`playwright_manager.py:1609`）等执行。
4. **观察**：`get_interactive_elements()`（`get_interactive_elements.py:214-260`）→ `wait_for_page_and_frames_load()` → `get_current_page()` → `do_get_accessibility_info(page)` → `flatten_elements()`（带 md 与上限截断）→ JSON。
5. **截图**：`take_browser_screenshot`/`capture_the_screen`（`browser_assist_tools.py:17-108`）用 `get_latest_screenshot_stream()` + PIL 保存；`take_screenshots`（`playwright_manager.py:1264`）。
6. **日志/证据**：`setup_request_response_logging`（`:1028`）、`log_request/log_response`（`:1034/1061`）、`setup_console_logging`（`:2065`）、trace（`_start_tracing`，`:512`）、video（`_launch_browser_with_video`，`:739`）→ 供 `core/invariants.py` 与 `reporting/bundle.py` 消费。
7. **浏览器版 Agent 的多模态**：`BrowserNavAgent` 继承 `MultimodalBaseNavAgent`（`browser_nav_agent.py:1-6`），后者用 `create_chat_model` 建视觉模型（`multimodal_base_nav_agent.py:55-61`）。
8. **移动分支**：`_create_mobile_nav_agent`（`simple_hercules.py:253-271`）双门控（`DEVICE_MANAGER=appium` + Appium 可导入）才创建；runner.shutdown 调用 `_teardown_appium_instances`（`runner.py:209-227`）。

## 6. 工具调用失败如何处理（问题 6）

见 `整体架构分析.md` 第 8 节表。核心机制：
- 工具异常 → `_execute_tool_call` 捕获 → `[TOOL ERROR] <name>: <e>`（`simple_hercules.py:965-967`），作为 ToolMessage 回灌 LLM，由 LLM 自行纠正/重试（导航 Agent prompt 通常给"一次纠错机会"，如 `api_nav_agent.py:55-57`、`mcp_nav_agent.py:58-60`）。
- 确定性断言工具内部异常 → 返回 `{"assertion":"ERROR", ...}` 而非抛出（`ui_assertions.py:331-338`、`api_assertions.py:325-332`）。
- 浏览器状态被改变 → 丢弃同批后续 tool_calls 并提示重读（`simple_hercules.py:1348-1370`）。
- Nav 轮次耗尽 → `[ERROR] ... max nav rounds ...`（`:1372-1380`）；helper 响应含 failure markers（"[error]"/"incomplete"/"max nav rounds" 等，`_helper_response_succeeded` `:135-149`）→ 不计入 completed steps。
- LLM/Planner 层失败 → 终局失败 JSON（`_planner_failure_result` 等）；场景整体崩溃 → `_failed_graph_result`。
- 清理/进程级失败 → `BaseExceptionGroup` 聚合 + cancellation 优先（`runner.py:90-114`、`playwright_manager.py:376-396`）；子进程超时 → 杀进程组（`run_manager.py:469-485`）。
- **注意**：Hercules 没有"断言失败即自动修复"的闭环；`healing/` 是独立旁路（分类+提案+探测），未接入 `_run_nav_agent` 的错误处理路径（源码中未见调用 `healing.*` 的主链路）。

## 7. 执行结果如何结构化输出（问题 7）

1. **GraphChatResult**（`utils/llm_helper.py:514-544`）：字段 `chat_history`、`messages`、`cost`、`terminate`、`last_helper_response`；`summary` 属性按优先级取：①终局 planner JSON（terminate=yes）→ ②终局 helper 响应（把 PASS/FAIL verdict 保住，且仅当 graph 结束或 helper 失败时信任）→ ③非终止 planner 响应。
2. **`parse_agent_response`**（`__main__.py:138` 调用）：把 summary 解析成 runner_result dict（含 `is_passed`/`is_assert`/`assert_summary`/`final_response`/`terminate`）；无结果/崩溃时合成显式失败 dict（`:141-171`）。
3. **JUnit XML**（`utils/junit_helper.py`）：`JUnitXMLGenerator.add_test_case`（`:326-478`）按 verdict policy 决定 `TestCase.result = Failure(...)` 或 pass；写入大量 property（Terminate、Feature File、Proofs Video/Screenshot、Network Logs、Agents Internal Logs、Planner Thoughts、Assertions *、cost/token）；`write_xml`/`merge_junit_xml`（`:480/520`）产出 `<feature>_result.xml`。
4. **HTML**：`__main__.py:265-269` 用第三方 `junit2htmlreport.runner.run` 把 XML 转 `<feature>_result.html`（best effort，失败仅告警）。
5. **Markdown 报告**：`reporting/markdown_report.py:243 generate_markdown_report`，输出 `Hercules_Test_Report.md`（`:19`）。
6. **失败 bundle**：`reporting/bundle.py:469 create_failure_bundles`：把 video/screenshot/network/trace/planner thoughts 聚合到 per-case 目录 + `bundle.md`（`:416`）。
7. **运行历史**：`reporting/run_db.py`：`RunHistory.record_run_summary`（`:917`）→ `start_run/finish_run/record_case/record_steps/record_healing_event`（`:501/554/604/678/707`），SQLite（WAL、竞争重试），支持 trend/flaky 查询。
8. **失败分类**（opt-in）：`__main__.py:335 _classify_failed_cases` → `healing/failure_classifier.classify_failure_with_context`，结果写入 bundle.md 与 history 的 healing 事件。
9. **退出码**：`__main__.py:418 compute_exit_code`、`_finalize_exit_code`（`:515`）；`STRICT_EXIT_CODE=true` 时测试失败→非 0（run_manager 子进程强制该变量，`:422`）。

## 8. 是否真的有独立 Assertion Agent（问题 8，最终答复）

**没有。** 详见第 3 节末尾与 `整体架构分析.md` 第 4.3 节。简明结论：

> 源码中未发现独立的 Assertion Agent 角色。实际断言判定由 **Planner（LLM）在决策 JSON 中自报 `is_passed/is_assert/assert_summary`** 完成，辅以**注册在导航 Agent 上的确定性断言工具**（`ui_assertions.assert_ui`、`api_assertions.assert_json_path`，其中 UI 断言默认关闭）和**报告期基于 `assertion_logs.log` 断言账本 / observer 不变量 / STRICT_VERDICT 的覆盖机制**。LangGraph 的 `assertion` 节点（`simple_hercules.py:1386-1423`）只是一个共享 planner verdict、写终局 JSON 的非 LLM 状态节点，并非独立 Agent。

## 9. 优点 / 缺陷 / 局限（问题 9，执行流程视角）

**优点**：verdict 有账本兜底；断言工具强调确定性与正对照；工具/LLM/进程失败全链路 containment；证据留痕与报告体系完善；UTC 时间统一。

**缺陷/局限**：
- **AGPL-3.0 强 copyleft**（第 13 条网络服务源码义务）；**Playwright 锁定 `<=1.49.0`**；复杂度高（见整体架构分析第 9 节）。
- **默认配置下事实层薄弱**：UI 断言、observer、分类、history、bundle 多默认关，默认 verdict 靠 LLM 自报，"零断言 pass"只标记不判红（`junit_helper.py:431-434`）。
- **断言与执行同源**：Planner 既是计划者又是 verdict 声明者，缺乏 Oracle 独立性；正确性依赖事后账本，而非前置独立判定。
- **自愈不闭环**：`healing/` 模块与主执行图隔离，提案/探测结果未反馈到 verdict 或重试策略（源码未见连线）。
- **启发式置信度**：失败分类 confidence 是命中占比（`failure_classifier.py:167-187`），不等于因果概率。
- **安全边界**：`execute_python_sandbox` 注入 page/browser/context/playwright_manager（`executor_nav_agent.py:19,91-95`）；heal LLM prompt 仅控制字符清洗 + 标记包裹不可信页面文本（`heal_proposer.py:40-66`）；未发现统一沙箱/权限模型（**尚未从源码核实**其隔离强度）。

## 10. 一个场景的端到端时序（源码串联）

1. `__main__.sequential_process()`：`process_feature_file` 拆分场景 → 每个场景 `stake_id = scenario` 清洗 → `serialize_feature_file` 得 command（`__main__.py:102-110`）。
2. `SingleCommandInputRunner.start()` → `initialize()`：读 `AgentsLLMConfigManager` 的 planner/nav/helper 配置 → `SimpleHercules.create()` 建 agents + graph → 建 PlaywrightManager（`runner.py:45-79`、`simple_hercules.py:151-227`）。
3. `process_command(cmd)` → `SimpleHercules.process_command`：initial state → graph.ainvoke（`simple_hercules.py:1550-1604`）。
4. Planner LLM 输出 strict JSON（`plan/next_step/target_helper/...`）→ 校验 → state 更新。
5. `target_helper` 路由到 nav agent；`_run_nav_agent` bind_tools 后循环：LLM 决定工具 → `_execute_tool_call` 调 `get_interactive_elements`/`click`/`assert_json_path`/... → ToolMessage 回灌 → 遇 `##TERMINATE TASK##` 退出。
6. helper 响应作为 HumanMessage 回 Planner；重复直到 Planner `terminate=yes`。
7. 若 `is_assert` → `_assertion_node` 写终局 JSON → END；否则直接 END（非断言终局）。
8. 若有 BINDING 不变量 → `_apply_invariant_failure` 强制判红。
9. `GraphChatResult` 返回 → `parse_agent_response` → `build_junit_xml`（verdict policy + 账本覆盖）→ HTML/Markdown/bundle/SQLite → 退出码。
