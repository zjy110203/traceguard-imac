# TraceGuard 状态机与结果判定规范

-   架构基线：v1.1
-   状态：状态与结果语义基线；转换条件和并发策略待详细设计

## 1. 设计原则

1.  不建立覆盖所有对象的全局状态机。
2.  每个领域对象拥有独立状态机。
3.  状态由对象所有者模块维护。
4.  Agent 不直接写入权威状态。
5.  状态转换必须有触发条件、权限、事件和失败处理。
6.  执行状态、测试结果、诊断状态和诊断结论分离。
7.  终态对象不得被普通重试操作覆盖；重试应创建新的执行尝试或新版本。

## 2. Task 状态机

建议状态：CREATED、QUEUED、RUNNING、WAITING、COMPLETED、FAILED、CANCELLED。

``` mermaid
stateDiagram-v2
    [*] --> CREATED
    CREATED --> QUEUED
    QUEUED --> RUNNING
    RUNNING --> WAITING
    WAITING --> RUNNING
    RUNNING --> COMPLETED
    RUNNING --> FAILED
    CREATED --> CANCELLED
    QUEUED --> CANCELLED
    RUNNING --> CANCELLED
    WAITING --> CANCELLED
```

Task 表示逻辑任务。WAITING 可用于等待审核、资源或依赖条件。具体是否需要
FINALIZING、是否允许 RUNNING 直接转 COMPLETED，应在详细设计中确定。

## 3. Run 状态机

建议状态：QUEUED、PREPARING、RUNNING、FINALIZING、COMPLETED、FAILED、TIMED_OUT、CANCELLED。

``` mermaid
stateDiagram-v2
    [*] --> QUEUED
    QUEUED --> PREPARING
    PREPARING --> RUNNING
    RUNNING --> FINALIZING
    FINALIZING --> COMPLETED
    PREPARING --> FAILED
    RUNNING --> FAILED
    PREPARING --> TIMED_OUT
    RUNNING --> TIMED_OUT
    QUEUED --> CANCELLED
    PREPARING --> CANCELLED
    RUNNING --> CANCELLED
    FINALIZING --> FAILED
```

Run 是一次具体执行尝试。重试创建新 Run，并保留前一次 Run 的状态和证据。

## 4. Step 状态机

建议状态：PENDING、RUNNING、PASSED、FAILED、SKIPPED、TIMED_OUT、CANCELLED、BLOCKED。

``` mermaid
stateDiagram-v2
    [*] --> PENDING
    PENDING --> RUNNING
    PENDING --> SKIPPED
    PENDING --> BLOCKED
    RUNNING --> PASSED
    RUNNING --> FAILED
    RUNNING --> TIMED_OUT
    RUNNING --> CANCELLED
```

SKIPPED 和 BLOCKED 必须有原因。跳过必需断言不能自动视为通过。

## 5. Diagnosis 状态机

建议状态：QUEUED、COLLECTING、TRIAGING、HYPOTHESIZING、PROBING、EVALUATING、COMPLETED、FAILED、CANCELLED。

``` mermaid
stateDiagram-v2
    [*] --> QUEUED
    QUEUED --> COLLECTING
    COLLECTING --> TRIAGING
    TRIAGING --> HYPOTHESIZING
    HYPOTHESIZING --> PROBING
    PROBING --> EVALUATING
    EVALUATING --> PROBING
    EVALUATING --> COMPLETED
    COLLECTING --> FAILED
    TRIAGING --> FAILED
    PROBING --> FAILED
    EVALUATING --> FAILED
    QUEUED --> CANCELLED
    COLLECTING --> CANCELLED
    PROBING --> CANCELLED
```

Diagnosis Status 描述诊断流程进度，不代表诊断结论。

## 6. ProbeExecution 状态机

建议状态：QUEUED、RUNNING、SUCCEEDED、FAILED、TIMED_OUT、BLOCKED、CANCELLED。

``` mermaid
stateDiagram-v2
    [*] --> QUEUED
    QUEUED --> BLOCKED
    QUEUED --> RUNNING
    RUNNING --> SUCCEEDED
    RUNNING --> FAILED
    RUNNING --> TIMED_OUT
    QUEUED --> CANCELLED
    RUNNING --> CANCELLED
```

BLOCKED 表示权限或策略阻止执行，不代表目标应用存在故障。

## 7. RepairProposal 生命周期

生命周期状态： - DRAFT - VALIDATING - VALIDATION_FAILED - VALIDATED -
PENDING_APPROVAL - APPROVED - REJECTED - PROMOTED - ROLLED_BACK

``` mermaid
stateDiagram-v2
    [*] --> DRAFT
    DRAFT --> VALIDATING
    VALIDATING --> VALIDATION_FAILED
    VALIDATING --> VALIDATED
    VALIDATED --> PENDING_APPROVAL
    PENDING_APPROVAL --> APPROVED
    PENDING_APPROVAL --> REJECTED
    APPROVED --> PROMOTED
    PROMOTED --> ROLLED_BACK
```

另设独立的 `sandbox_validation_status`，例如
NOT_STARTED、RUNNING、PASSED、FAILED、TIMED_OUT、BLOCKED。生命周期状态与沙箱执行状态不能混用。

正式晋升还应满足： - Diff 在允许范围； - 原始 Assertion 得到保护； -
Oracle 未被修改； - 沙箱检查通过； - 相关回归通过； - 审批有效； - 目标
TestCaseVersion 与审批时一致。

## 8. RegressionCampaign 状态机

建议状态：CREATED、RUNNING、PASSED、FAILED、INCONCLUSIVE、CANCELLED。

``` mermaid
stateDiagram-v2
    [*] --> CREATED
    CREATED --> RUNNING
    RUNNING --> PASSED
    RUNNING --> FAILED
    RUNNING --> INCONCLUSIVE
    CREATED --> CANCELLED
    RUNNING --> CANCELLED
```

部分用例未执行、必需用例失败和环境故障的聚合规则待详细设计。

## 9. 四个独立结果维度

  字段                回答的问题
  ------------------- ------------------------
  execution_status    执行过程发生了什么
  test_verdict        测试是否符合预期
  diagnosis_status    诊断流程进行到什么阶段
  diagnosis_outcome   故障原因是否得到确认

示例：

``` json
{
  "execution_status": "COMPLETED",
  "test_verdict": "FAILED",
  "diagnosis_status": "COMPLETED",
  "diagnosis_outcome": "PROBABLE"
}
```

含义：执行正常结束，测试确认失败，诊断流程完成，但根因只有较强支持而未确认。

## 10. Test Verdict 判定规范

  -----------------------------------------------------------------------
  结果                                规则
  ----------------------------------- -----------------------------------
  PASSED                              所有必需 Assertion
                                      均得到有效评估且通过

  FAILED                              至少一个必需 Assertion 被确认失败

  INCONCLUSIVE                        没有确认失败，但至少一个必需
                                      Assertion 无法确定或未完整评估

  NOT_EVALUATED                       没有任何必需 Assertion 得到有效评估
  -----------------------------------------------------------------------

判定逻辑： 1. 任何必需断言确认失败，整体 FAILED。 2.
没有确认失败，但至少一个必需断言不确定或未完成，整体 INCONCLUSIVE。 3.
所有必需断言均通过，整体 PASSED。 4. 没有任何必需断言得到有效评估，整体
NOT_EVALUATED。

补充： - Oracle 不可用不是 PASSED。 - 未执行断言不能被补成通过。 -
非必需断言是否影响整体结果，由用例策略明确。 -
执行中断前已确认必需断言失败，仍保留 FAILED。 - 部分执行结果保留每个
Assertion 的独立状态。

## 11. Diagnosis Outcome

  结果           含义
  -------------- --------------------------------------
  CONFIRMED      满足明确的证据确认规则
  PROBABLE       有较强支持，但仍存在不确定性
  INCONCLUSIVE   证据不足、冲突无法解决或诊断预算耗尽

多根因允许并存。每个 Hypothesis 独立保存支持、反驳、状态和证据。

## 12. 故障表现与根因分类

必须区分： - Symptom：失败表现； - Root Cause：根本原因； - Contributing
Factor：促成因素； - Flaky Characteristic：不稳定特征。

Flaky
不是唯一根因类别，可能由产品、环境、测试数据、时序或自动化代码共同导致。

## 13. 状态转换统一要求

每个转换应定义当前状态、目标状态、触发事件或命令、发起者、权限要求、前置条件、数据副作用、领域事件、幂等策略、超时、重试、取消和失败补偿。

## 14. 待确认事项

-   Task WAITING 的细分原因；
-   Run 终结与 FINALIZING 语义；
-   Step 是否允许重试及如何表示；
-   Diagnosis 恢复和人工介入状态；
-   Repair 多轮验证如何表达；
-   RegressionCampaign 聚合判定；
-   取消请求与 Worker 实际停止之间的状态；
-   状态事件和数据库事务一致性。
