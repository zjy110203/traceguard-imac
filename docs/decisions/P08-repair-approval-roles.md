# P08 决策提案：Repair 审批角色与职责分离（待评审，未冻结）

> 状态：**NEEDS_REVIEW**。不擅自认定任何角色拥有正式审批权限；当前实现只校验
> "非 Agent 的具名审批人"，属于临时安全底线，不是组织权限模型。

## 1. 现状

| 环节 | 实现 | 缺口 |
|---|---|---|
| 提案 | `created_by` 记字符串（`agent:repair-planner`） | 未区分人/Agent 账号 |
| 审批 | `approver` 不得包含 `agent/llm` | 不校验审批人角色、不校验职责分离 |
| 晋升 | 系统自动（CAS） | 谁有权触发晋升未定义 |
| 回滚 | `operator` 字符串 | 谁有权回滚未定义 |
| 拒绝/重提 | 支持 REJECTED；重提需回到 DRAFT（当前不自动） | 重提流程未定义 |
| 审计 | `approval_ref` 含审批人/时间/备注 | 未落独立审计表 |

当前实现可支撑"有审批动作"，但**不能声称具备 RBAC**。

## 2. 角色候选

| 角色 | 职责 | 建议权限 |
|---|---|---|
| `author`（用例作者/测试工程师） | 提出修复、沙箱验证 | 创建/修改自己的 DRAFT；提交审批 |
| `qa-lead`（测试负责人） | 审批修复、把关断言质量 | 批准/拒绝；查看全部 |
| `platform-admin` | 晋升、回滚、处理平台级异常 | 晋升/回滚；不可批准（职责分离） |
| `agent:*` | 自动生成候选（不可审批） | 创建候选；只读 |

## 3. 候选方案

### 方案 1：单人审批（最低要求）

- 任意非 Agent 的 `qa-lead` 可批准；提案人不得审批自己的提案。
- 优点：简单；缺点：单点，缺少高风险场景的双人复核。

### 方案 2：职责分离 + 高风险双人（推荐）

- 常规修复：`author` 提交 → `qa-lead` 批准（提案人 ≠ 审批人）。
- 高风险修复（如涉及 `test_data_refs`、影响多条断言的数据准备）：
  需要 2 名不同 `qa-lead` 批准，或 1 名 `qa-lead` + `platform-admin`。
- 晋升：仅 `platform-admin`；回滚：`qa-lead` 或 `platform-admin`，必须填写原因。
- 优点：符合职责分离；缺点：流程变长，需要身份系统支撑。

### 方案 3：全自动（仅平台管理员事后审计）

- 沙箱通过即晋升，事后审计。
- 风险：与"Agent 不得自批自修"原则冲突。**不推荐**。

## 4. 推荐的权限矩阵（待批准）

| 操作 | author | qa-lead | platform-admin | agent |
|---|---|---|---|---|
| 创建提案 | ✓ | ✓ | ✓ | ✓ |
| 规则校验 / 沙箱 | ✓ | ✓ | ✓ | ✗ |
| 提交审批 | ✓ | ✓ | ✓ | ✗ |
| 批准 / 拒绝 | ✗ | ✓（非本人提案） | ✗（职责分离） | ✗ |
| 晋升 | ✗ | ✗ | ✓ | ✗ |
| 回滚 | ✗ | ✓（需原因） | ✓ | ✗ |

## 5. 实现影响

1. `RepairService.approve` 增加 `approver_role` 与"提案人 ≠ 审批人"校验；
2. 新增 `tg_audit` 表或复用 `tg_doc(kind=audit)` 记录每个动作；
3. API 增加 `X-Actor` / `X-Role` 头（由前置网关注入，禁止客户端自报）；
4. 前端按钮按角色显示（当前为全量显示）。
