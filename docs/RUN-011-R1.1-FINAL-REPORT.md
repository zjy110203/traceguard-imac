## 0. 最终回答指令 §九 的十个问题

**Q1：Workspace 是否真正隔离？**
**是。** 实体 Workspace 由服务端数据库行确定，不再信任请求体/query 声明。新增
`apps/api/traceguard_api/workspace.py` 统一出口（`principal_of` / `require_entity_workspace` /
`scope_filter` / `filter_by_workspaces`），detail/写路由逐实体授权，列表省略 `workspace_id`
只返回调用方有权范围、指定无权 Workspace 返回 403。`tests/integration/test_workspace_isolation_run011_r1_1.py`
9 用例全绿，A/B 两个独立 Workspace + 各自 viewer/qa-engineer/qa-lead（无一方使用 `*`），
正向可读、负向 14 条跨空间路径全部 403 且数据库零非法写入（WP1 报告）。

**Q2：是否还存在跨 Workspace 数据读取？**
**否（已验证路径内）。** 负向测试覆盖读取 B 的 Task/Run/Report/Evidence/Events/
Diagnosis/ProbePlan/Repair、用 B 的 TestCase 建 Task、用 B 的 Run 建 Probe Plan、
用 B 的 Diagnosis 建 Repair、操作 B 的 Repair（validate/sandbox/submit/approve/reject/
reconcile），逐 ID 全部拒绝，且校验 `tg_task`/`tg_run`/`tg_evidence`/`tg_doc`/`tg_intent`
行数无新增、无跨空间 Evidence 引用、无对象枚举、拒绝审计含真实 actor（WP1 报告 §3）。
两轮闭环 DB 复核逐实体校验 Workspace（loop1/loop2 各 24/24，`dsn_scheme=postgresql+psycopg`）。
**边界说明**：前端无 workspace 切换控件（硬编码 `default`），这是既有产品缺口，非本轮新增；
UI 层面的跨空间操作由 API 层测试覆盖，UI 验收如实登记该缺口（WP6 报告 §3）。

**Q3：Task/Run/Probe/Repair 是否使用正确 Workspace？**
**是。** `TaskService.create_task()` 的 `workspace_id` 改为必填（空值 fail-closed）；
`POST /tasks` 与 `/testcases/{id}/execute` 从 TestCaseVersion 行解析权威 Workspace；
`create_run()` 校验版本存在、属于 `Task.testcase_ref`、Workspace 与 Task 一致；
`ProbeService` 的 budget/execution/plan workspace 从 Run/Diagnosis 反查，不再信任请求体；
`RepairService.sandbox_run()` 的 Sandbox TestCase/Task/Run 显式继承 Repair Workspace。
两轮闭环逐实体检查（T1–T18 + workspace 逐 ID 校验）全部通过，24/24 ×2。

**Q4：Repair 的来源是否可信？**
**是。** 服务端按来源分类强制可信：`human:*` 来自已认证 Principal（`trusted_actor` 忽略
声明主体、校验动作权限、写审计）；`rule:*` 只由受信内部规则路径写入；`llm:*` 只在真实
LLM Advisor 成功返回并通过校验时标记。伪造 `repair_source="llm:*"` / 伪造 `created_by`
被服务端拒绝（WP3 报告 §3.4，负向测试）。两轮闭环如实标注实际来源 `rule:locator-fixture`，
LLM 规划器记录 `called=false`，未冒充 Agent 自动推导。

**Q5：Repair 的 Diagnosis/Run 关联是否由服务端验证？**
**是。** 创建 Proposal 时校验：Diagnosis 真实存在、`kind` 正确、`testcase_id` 匹配、
`run_id == source_run_id`、Workspace 一致；source Run 真实存在、同 TestCase、
版本对应 base_version、具备真实失败/NOT_EVALUATED 证据，**PASSED Run 不能伪装失败来源**；
不匹配即拒绝，不再把调用方两个字符串原样入库。负向测试覆盖不存在的 diagnosis_id、
Diagnosis/Run/TestCase/Workspace 不匹配、PASSED Run 作来源、跨 TestCase 版本（WP3 报告）。

**Q6：两轮完整闭环是否通过？**
**是。** PG16（两独立库 `traceguard_r11_l1/l2`）+ 独立 API + 独立 Worker×3 + TeamFlow
+ 真实 Chromium（bundled 159.0.8154.6，egress_enforced=true）+ 认证开启 + 强制 Egress，
两个不同 Workspace（`ws-r11-1` / `ws-r11-2`）各跑 18 步：
Intent → Exploration → Compile → Oracle → Approval → Run → Diagnosis → Probe →
Repair → Sandbox → Human Approval → Promotion → Regression → Rollback。
API 侧 **86/86 ×2**、DB 逐实体复核 **24/24 ×2**，均 0 失败：
`docs/assets/run011-r1.1/lineage/loop{1,2}.json` 与 `loop{1,2}-db.json`。

**Q7：Benchmark 的指标是否可信？**
**口径已修正，指标按修正后口径可信。** F/G 臂正名为 `F_probe_post_hoc_aware` /
`G_probe_unknown_time` 并明确"当前 Benchmark 未产生 Run 内 ALIGNED 探针证据"；
C=24/37=0.6486、F=G=26/37=0.7027，仅 2/37 从 INCONCLUSIVE 变 PROBABLE，
**不宣称时间对齐显著提高准确率**；拆分 LLM 成功 21/37、invalid_json 16/37、
成功子集 13/21、H 混合臂 0.6216，区分 Fallback 与 LLM 自身准确率；
单独统计探针 54 次、假设更新 25 次（15 SUPPORT / 10 CONTRADICT / 0 CONFIRM / 0 EXCLUDE）。
保留原始数据、不覆盖历史 JSON（WP3-BENCHMARK-ERRATA 报告）。

**Q8：UI 是否真正完成业务验收？**
**部分完成（如实登记）。** 新增真实 Chromium + 真实 API（认证+CSRF+Vue 正式产物）
UI 验收，四角色独立 context，15/15 检查通过且每项带服务端 API 回读证据：
401 跳登录、viewer 只读/403、qa-engineer 建需求与用例落库、platform-admin 建用户落库、
跨 workspace 写被拒、审核门禁正确拒绝。截图 6 张 + JSON 证据归档于
`docs/assets/run011-r1.1/ui/`。**未完成项**：前端无 workspace 切换控件；审核成功路径
（需 Oracle 绑定 + 稳定性回放）由两轮闭环脚本覆盖而非 UI 点击。不伪装这两项为 UI 通过。

**Q9：Worker 故障恢复有哪些仍然 BLOCKED？**
**B-17 保持 BLOCKED（未解除）。** RUN-008 登记的补充故障矩阵 4 场景因 AgentDR 两次拦截

被拦截操作、不更换工具规避、不导出凭据。既有真实证据仍有效（
`docs/assets/run008/wp3/worker-fault-recovery.json` 17/17、`worker-concurrency.json` 4 Worker
峰值 4/单 Run 单 owner），不作为 BLOCKED 场景的通过证据。B-18（60 分钟长稳）此前已解除。

**Q10：是否具备进入 RUN-012 的条件？**
**具备（带明确边界）。** P0/P1 安全修复全绿、两轮闭环与 DB 逐实体复核全绿、
PG16 全量回归通过、Ruff 全绿、Benchmark 口径修正、UI 验收有真实证据。
