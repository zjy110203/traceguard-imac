# TraceGuard 核心数据模型与领域边界

-   架构基线：v1.1
-   状态：领域对象和职责边界基线；数据库物理 Schema 待设计
-   说明：本文字段仅为概念说明，不替代正式 C01～C12 Schema。

## 1. 设计目标

明确核心业务对象、对象关系、唯一业务写入责任模块、读取和变更边界，以及历史执行和证据的追溯方式。

## 2. 六个核心数据领域

  ------------------------------------------------------------------------------------------------------------------------
  领域                    核心对象                                                            主要问题
  ----------------------- ------------------------------------------------------------------- ----------------------------
  测试需求                TestIntent                                                          要测试什么

  测试资产                TestCase、TestCaseVersion、OracleSpec                               如何测试、正确预期是什么

  执行                    Task、Run、Step                                                     测试如何执行

  事件与证据              Event、Evidence、EvidenceEdge                                       实际发生了什么，有什么证据

  诊断                    Hypothesis、ProbeExecution、Diagnosis                               为什么失败，结论有多确定

  处置与修复              Disposition、Defect、RepairProposal、Approval、RegressionCampaign   下一步如何处理
  ------------------------------------------------------------------------------------------------------------------------

Benchmark 另有 Dataset、GroundTruth、Experiment 和 EvaluationResult
等对象。

## 3. 核心对象说明

### 3.1 TestIntent

描述测试目标、需求来源、业务场景和候选验收条件。

概念属性：intent_id、title、description、requirement_refs、business_context、preconditions、candidate_assertions、owner、status、version。

### 3.2 TestCase 与 TestCaseVersion

TestCase 代表逻辑测试用例；TestCaseVersion 代表不可变的具体版本。

版本内容包括： - 测试步骤； - Locator 策略； - Assertion； -
测试数据要求； - 前置条件； - 后置条件； - 清理策略； - 运行配置； -
Oracle 引用。

历史 Run 必须绑定当时实际使用的
TestCaseVersion，不能只引用一个会变化的当前版本指针。

### 3.3 OracleSpec

描述某个 Assertion 的可信预期和实际观测方式。

概念属性： - oracle_id； - assertion_id； - expected_behavior； -
requirement_ref； - expectation_approval； - primary_oracle； -
supporting_oracles； - evaluation_rule； - consistency_window； -
required； - version。

正式预期必须具备可信来源和审核记录。

### 3.4 Task

逻辑测试任务，可以产生多次
Run。负责任务目标、被测应用、测试资产版本引用、调度、取消、重试策略和任务级汇总。

### 3.5 Run

一次具体执行尝试。应保存 task_id、TestCaseVersion、OracleSpec
版本、浏览器和 Runner
版本、执行配置、环境标识、开始和结束时间、execution_status、test_verdict。

重试产生新的 Run，不覆盖历史 Run。

### 3.6 Step

Run 中的具体执行步骤。应关联步骤定义、实际操作、时间、Step
状态、错误信息、Event 和 Evidence。

### 3.7 Event

系统运行中发生的事件。Event 是发生事实的记录，不等于诊断证据。

建议包含唯一事件 ID、事件类型、Schema 版本、Run/Step
上下文、生产者标识、生产者实例标识、局部序号、发生时间、接收时间、幂等键、关联标识和
Payload。

### 3.8 Evidence

用于支持或反驳 Assertion、Hypothesis 或事实判断的证据。

建议区分： - Raw Evidence； - Normalized Evidence； - Derived
Evidence； - Diagnostic Evidence。

Evidence 需要保留来源、内容完整性、来源可信度、时间有效性和派生链。

### 3.9 EvidenceEdge

描述两个节点之间的结构、关联或诊断关系。

关系类型建议： - parent_child； - emitted_by； - derived_from； -
correlated_by_trace_id； - correlated_by_request_id； -
same_execution_context； - temporal； - supports； - contradicts； -
evaluates。

### 3.10 Hypothesis

诊断过程中的候选故障解释。应记录假设内容、类别、支持证据、反驳证据、当前状态、更新历史、置信度或等级、相关探针。允许多个
Hypothesis 并存。

### 3.11 ProbeExecution

一次具体探针执行。应记录 Probe
定义版本、目标、权限决策、风险等级、是否只读、执行预算、状态、结果、Evidence
和失败或阻断原因。

ProbeExecution 失败不等于目标故障成立。

### 3.12 Diagnosis

一次完整诊断结果。应保留
diagnosis_status、diagnosis_outcome、候选根因、促成因素、支持与反驳证据、探针执行历史、未解决冲突、停止原因和结论依据。

### 3.13 Disposition

描述诊断结果的处置方向，例如产品缺陷、测试资产问题、环境问题或不确定。Disposition
不等于 Diagnosis，不得覆盖原始诊断结果。

### 3.14 RepairProposal

描述候选测试资产修复方案。应关联原 TestCaseVersion、修改
Diff、修改原因、受影响 Assertion、Oracle
引用、沙箱验证、审批、回归结果、晋升版本。

### 3.15 Approval

独立记录审批人、审批动作、审批时间、依据和审批对象版本。Approval Manager
管理审批记录，不直接拥有 RepairProposal 的业务生命周期。

### 3.16 RegressionCampaign

组织一组修复后回归测试，保存目标范围、执行集合、结果和失败原因。

## 5. 五组关键对象边界

  --------------------------------------------------------------------------------------------
  边界                                含义
  ----------------------------------- --------------------------------------------------------
  TestIntent ≠ TestCase               意图描述目标，用例描述可执行步骤

  Task ≠ Run                          Task 是逻辑任务，Run 是执行尝试

  Event ≠ Evidence                    Event 是发生记录，Evidence 是用于证明或分析的材料

  Test Verdict ≠ Diagnosis Outcome    一个判断测试是否符合预期，一个判断故障原因是否得到确认

  Diagnosis ≠ Disposition             一个解释问题，一个决定处置方向
  --------------------------------------------------------------------------------------------

## 6. 数据所有权

  对象                         唯一业务写入责任模块
  ---------------------------- -----------------------------------------
  TestIntent                   Test Intent Manager
  TestCase / TestCaseVersion   TestCase Service
  OracleSpec                   Oracle Manager
  Task                         Execution Orchestrator
  Run / Step                   Execution Engine
  Event                        Event Collector
  Evidence                     Evidence Manager
  EvidenceEdge                 Evidence Correlation Service
  Hypothesis                   Diagnosis Workflow / Hypothesis Manager
  ProbeExecution               Probe Engine
  Diagnosis                    Diagnosis Workflow
  Disposition                  Disposition Router
  Defect                       Defect Management
  RepairProposal               Repair Service
  Approval                     Approval Manager
  RegressionCampaign           Regression Manager

其他模块可以通过接口读取或请求变更，但不得绕过所有者修改权威状态。

## 7. 数据不变量

1.  已创建的 TestCaseVersion 不原地覆盖。
2.  OracleSpec 的正式预期不能由 Agent 自动改写。
3.  Run 绑定具体 TestCaseVersion 和 OracleSpec 版本。
4.  重试创建新的 Run。
5.  历史 Event 不因新执行而覆盖。
6.  Evidence 保留原始来源或派生来源。
7.  Evidence 内容完整性和来源可信度分开表示。
8.  Diagnosis 保留支持和反驳证据。
9.  Probe 被阻断不等于目标故障成立。
10. Approval 是独立审计对象。
11. RepairProposal 不能通过删除或弱化 Assertion 获得通过。
12. Ground Truth 不暴露给被测 Agent。
13. 业务状态以权威持久化记录为准，不以模型输出文本为准。

## 8. 数据存储建议

  数据                    建议存储
  ----------------------- ---------------------------------------
  业务对象和状态          PostgreSQL
  Event 元数据和索引      PostgreSQL 或独立事件存储，按规模评估
  截图、视频、HAR、附件   MinIO / 对象存储
  短期缓存                Redis
  工作流检查点            LangGraph Checkpointer，具体后端待定
  Ground Truth            独立受控数据域和访问策略

首期不强制图数据库。Evidence Graph
可以先通过关系表、索引和查询服务实现；是否需要专用图存储由数据规模和图查询复杂度决定。
