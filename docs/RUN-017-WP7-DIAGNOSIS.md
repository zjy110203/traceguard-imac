### 3.1 DB-004 与 TIME-003：不是规则写错，是证据不足

- **DB-004**：`count=0` 在 Run 时与 TF-DB-001（事务回滚）**完全同签名**，
  引擎已把 PERSISTENCE 标为"候选（非确认）"，但因它是唯一 SUPPORTED 假设，
  方向性预测仍落到 PERSISTENCE。要区分必须"延迟复测"——正是 WP2 的
  `state_consistency` 探针在做的事。**在没有探针回灌的前提下，这是诚实的上限。**
- **TIME-003**：双提交的第二次点击发生在页面跳转后，证据只表现为"元素找不到"，
  LOCATOR 是当时证据下最合理的解释。

### 3.2 已修复的真实缺陷：5xx 存在时 UI 渲染被错误确认

**现象**：TF-FLAKY-002（50% 概率 500）第一轮，页面出现错误提示导致成功横幅断言失败，
引擎在存在 5xx 的情况下仍把 `UI_RENDERING` 标为 `confirming=True`，输出 CONFIRMED。

**为什么是缺陷**：同一文件里"持久化"规则已经写明"若存在 5xx，未落库是接口失败的后果，
不作为独立根因"；UI 渲染却缺少同一条约束——**症状冒充了根因**。

**修复**（`diagnosis_service.py`）：

```python
# 无 5xx：UI 渲染可作为确认级假设
supporting=refs(ui_ids or state_ids, confirming=not http_5xx),
contributing_factors=(["检测到接口 5xx：界面缺失可能是接口失败的后果，不作为独立根因"]
                      if http_5xx else []),
```

**验证**：单测/集成 22 项通过；对 TF-FLAKY-002 重放 2 轮，第二轮预测从
`UI_RENDERING` 修正为 `API`（第一轮该 Run 的网络证据里没有 5xx，仍给 UI_RENDERING——
这是证据不足，不是规则回退）。

### 3.3 UI-002 / NET-002 为什么会弃权（而不是硬猜）

- UI-002（静默忽略）：页面无请求、无反馈、业务未落库。Run 内证据只有"没有发生任何事"，
  引擎无法区分"前端没提交"与"提交了但后端没收到"；
- NET-002（9s 延迟）：Run 内只有超时错误，缺少"业务是否最终成功"的状态回读。

两者都能被 WP2 的浏览器观测/状态一致性探针补上，但**诊断引擎不读探针以外的评测标签**，
因此保持 INCONCLUSIVE。

## 4. 本轮**没有**做的事（避免为指标过拟合）

- 没有为 DB-004/TIME-003 写"看到 9s 就判 TIMING"的规则；
- 没有把 `root_causes` 的阈值调低来"多确认几个"；
- 没有删除任何失败样本，也没有修改历史实验数据；
- 没有引入 LLM 直接产出 CONFIRMED 的路径。

## 5. 后续最值得做的三件事（带验收标准）

| 优先级 | 改进 | 验收标准 |
|---|---|---|
| P0 | 把 `state_consistency` 探针结果回灌诊断（延迟复测） | DB-003/004 的方向性预测从 PERSISTENCE 变为 TIMING；不得影响 DB-001 判 PERSISTENCE |
| P1 | 请求级 5xx 与失败步骤做时间对齐 | FLAKY-002 两轮均预测 API；UI 类样本不被 5xx 污染 |
| P1 | 为"无反馈/超时"场景补独立状态回读证据 | UI-002/NET-002 从 INCONCLUSIVE 变为可确认，且误判率不升 |

三项都需要**独立保留样本**验证（本轮 60 样本可作开发集，另需新场景作保留集），
在此之前不宣称诊断质量"已提升"。

## 6. 结论

- 本轮诊断在**新口径**下：CONFIRMED 口径 93.75%（n=16）、方向性 83.33%（n=30）；
- 发现并修复 1 个真实规则缺陷（5xx 存在时 UI 渲染被错误确认）；
- 其余错误均为**证据不足**，已逐条登记，不用硬编码掩盖；
- 诊断质量仍是 **PARTIAL**：样本量小、无保留集、探针回灌未接通。
