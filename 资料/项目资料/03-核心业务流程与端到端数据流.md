# TraceGuard 核心业务流程与端到端数据流

-   架构基线：v1.1
-   重点场景：TeamFlow 创建项目
-   状态：业务流程基线；具体 API 路径和消息 Schema 待详细设计

## 1. 文档目的

本文从真实业务场景解释 TraceGuard
的模块协作方式，明确用户请求、模块处理、数据对象、事件和证据流转、诊断以及处置出口。

## 2. 端到端主流程

``` mermaid
flowchart TD
    A["用户提交测试需求"]
    B["Test Intent Manager"]
    C["Explorer Agent / 人工测试设计"]
    D["Exploration Trace"]
    E["TestCase Compiler"]
    F["Candidate TestCase + Candidate Oracle"]
    G["人工审核 / Oracle 批准"]
    H["TestCase Service + Oracle Manager"]
    I["Execution Orchestrator 创建 Task"]
    J["Execution Engine 创建 Run / Step"]
    K["Playwright 执行"]
    L["Event Collector"]
    M["Evidence Manager"]
    N["Evidence Correlation Service"]
    O["Failure Triage / Diagnosis"]
    P["Disposition Router"]
    Q["报告 / 缺陷 / 修复建议"]

    A --> B --> C --> D --> E --> F --> G --> H
    H --> I --> J --> K --> L --> M --> N --> O --> P --> Q
```

首期纵向切片允许跳过自主探索和自动编译，直接使用人工编写并审核的
TestCase，但 Oracle、执行、事件、证据、诊断和处置链路仍需完整。

## 3. 场景定义：创建项目

用户需求："验证用户能够创建项目，创建成功后项目能够真实持久化，并且能够在项目列表中查询到。"

前置条件： - TeamFlow 可访问； - 测试用户已登录； -
测试用户具有创建项目权限； - 测试 Workspace 存在； -
测试数据命名空间可用； - 业务状态查询接口经过授权； -
测试后清理策略已经定义。

候选 Assertion：

  Assertion   预期                     Primary Oracle 候选
  ----------- ------------------------ ---------------------------
  A1          页面显示创建成功反馈     UI
  A2          项目数据真实持久化       独立业务状态查询
  A3          项目列表能查询到该项目   UI 或业务查询，按目标确定
  A4          创建接口返回预期状态     API

每个 Assertion 独立指定 Primary Oracle 和 Supporting
Oracles，不建立全局固定 Oracle 排名。

## 4. 测试资产准备流程

``` mermaid
sequenceDiagram
    actor User as 测试人员
    participant Intent as Test Intent Manager
    participant Explorer as Explorer Agent
    participant Compiler as TestCase Compiler
    participant Oracle as Oracle Manager
    participant Case as TestCase Service

    User->>Intent: 提交创建项目需求
    Intent-->>User: 返回结构化 TestIntent
    User->>Explorer: 发起探索（或使用人工步骤）
    Explorer->>Explorer: 观察页面、执行操作、记录轨迹
    Explorer-->>Compiler: Exploration Trace
    Compiler->>Compiler: 规范化步骤、解析 Locator、构造断言
    Compiler-->>User: Candidate TestCase / Oracle
    User->>Oracle: 审核预期来源和 Oracle 规则
    Oracle-->>User: 审核结果
    User->>Case: 批准候选 TestCase
    Case-->>User: 创建正式 TestCaseVersion
```

正式资产晋升前至少需要： - 需求来源可追溯； - 步骤和目标明确； - Locator
通过检查； - Assertion 有明确预期； - Oracle 有可信来源； -
测试数据可重复准备； - 后置条件和清理策略明确； - 审核记录完整。

## 5. 执行流程

``` mermaid
sequenceDiagram
    actor User as 用户
    participant API as FastAPI
    participant DB as PostgreSQL
    participant Queue as Celery
    participant Worker as Execution Worker
    participant Engine as Playwright Engine
    participant Target as TeamFlow
    participant Event as Event Collector

    User->>API: 创建执行请求
    API->>DB: 创建 Task
    API->>Queue: 投递执行任务
    API-->>User: 返回 task_id
    Queue->>Worker: 分发任务
    Worker->>DB: 创建 Run
    Worker->>Engine: 加载 TestCaseVersion / OracleSpec
    Engine->>Target: 执行 UI 操作
    Target-->>Engine: 页面和网络响应
    Engine->>Event: 上报 Execution Events
    Event->>DB: 持久化事件
    Engine->>DB: 保存 Step 和执行结果
    Engine->>DB: 保存 Run 终态
    API-->>User: 查询或订阅执行状态
```

说明： - Task 是逻辑任务。 - Run 是一次具体执行尝试。 - 重试产生新的
Run，不覆盖历史 Run。 - Worker 任务重复投递时需要幂等。 -
浏览器上下文和执行资源需要隔离。 - 业务状态最终以持久化记录为准。

## 6. Event 到 Evidence 的数据流

``` mermaid
flowchart LR
    A["Playwright / Browser / API / Probe"]
    B["Event Envelope"]
    C["Event Collector"]
    D["Event Store"]
    E["Evidence Extractor"]
    F["Raw Evidence"]
    G["Normalized Evidence"]
    H["Derived Evidence"]
    I["Evidence Manager"]

    A --> B --> C --> D --> E
    E --> F
    E --> G
    G --> H
    F --> I
    G --> I
    H --> I
```

一个事件不一定等于一条证据；一条证据也可能由多个事件或原始附件派生。原始证据应尽可能保留，不应只保留模型总结。

## 7. Evidence Graph 建立流程

``` mermaid
flowchart TD
    A["Evidence Records"]
    B["提取来源标识"]
    C["提取 Trace / Request / Run / Step 关联"]
    D["建立结构关系"]
    E["建立关联关系"]
    F["建立诊断推理关系"]
    G["检查来源独立性"]
    H["Evidence Graph"]

    A --> B --> C
    C --> D
    C --> E
    A --> F
    D --> G
    E --> G
    F --> G
    G --> H
```

关系必须区分结构与来源、关联、诊断推理。时间接近只能建立 temporal
关系，不能自动推导因果。

## 8. 诊断流程

``` mermaid
sequenceDiagram
    participant Triage as Failure Triage
    participant Workflow as Diagnosis Workflow
    participant Hyp as Hypothesis Manager
    participant Planner as Active Diagnosis Planner
    participant Policy as Permission / Risk Policy
    participant Probe as Probe Engine
    participant Evidence as Evidence Manager

    Triage->>Workflow: 提交失败上下文
    Workflow->>Hyp: 生成候选假设
    Hyp-->>Workflow: Hypothesis Set
    Workflow->>Planner: 提交证据缺口和预算
    Planner->>Policy: 请求探针权限检查
    Policy-->>Planner: 允许 / 拒绝
    Planner->>Probe: 执行获准探针
    Probe->>Evidence: 提交探针结果和 Evidence
    Evidence-->>Hyp: 新证据
    Hyp->>Hyp: 更新支持、反驳和不确定性
    Hyp-->>Workflow: 诊断状态
    Workflow-->>Triage: Diagnosis Result
```

探针执行失败只能说明 ProbeExecution 未成功，不代表目标故障成立。

## 9. 诊断后的处置流程

``` mermaid
flowchart TD
    A["Diagnosis"]
    B["Disposition Router"]

    B --> C["Product Defect"]
    B --> D["Test Asset Issue"]
    B --> E["Environment / Data Issue"]
    B --> F["Timing / Flaky"]
    B --> G["Agent / Automation Issue"]
    B --> H["Inconclusive"]

    C --> I["Defect Record"]
    D --> J["Repair Proposal"]
    E --> K["环境 / 数据处理"]
    F --> L["稳定性分析"]
    G --> M["自动化链路分析"]
    H --> N["补充证据 / 人工复核 / 归档"]
```

"测试失败"不等于"产品缺陷"，更不等于"应该自动修改代码"。

## 10. 安全修复与回归流程

``` mermaid
sequenceDiagram
    participant Advisor as Repair Advisor
    participant Repair as Repair Service
    participant Sandbox as 隔离沙箱
    participant Oracle as Oracle Manager
    participant Approval as Approval Manager
    participant Regression as Regression Manager
    participant Case as TestCase Service

    Advisor->>Repair: 提交 Repair Proposal
    Repair->>Sandbox: 应用候选 Diff
    Sandbox->>Oracle: 读取已批准 Oracle（只读）
    Sandbox->>Sandbox: 静态检查、回放和断言保护
    Sandbox-->>Repair: 验证结果
    Repair->>Approval: 请求人工审批
    Approval-->>Repair: 批准 / 拒绝
    Repair->>Regression: 创建回归任务
    Regression-->>Repair: 回归结果
    Repair->>Case: 晋升新 TestCaseVersion
```

此流程为目标设计。具体晋升条件、审批策略和回归范围需要在 Repair
契约和状态机设计中冻结。

## 11. 异常分支

  ----------------------------------------------------------------------------
  异常                                预期处理
  ----------------------------------- ----------------------------------------
  缺少 TestCase                       不执行，返回上下文缺失

  缺少必需 Oracle                     不得判定 PASSED；按评估情况输出
                                      NOT_EVALUATED 或 INCONCLUSIVE

  Worker 崩溃                         记录执行异常，按幂等和恢复策略处理

  Event 重复                          消费端去重

  Event 乱序                          保留发生时间、接收时间和生产者局部序号

  Evidence 附件缺失                   标记证据缺失，不伪造内容

  Probe 被拒绝                        记录 BLOCKED，不更新目标假设为已确认

  证据冲突                            保留冲突，必要时 INCONCLUSIVE

  修复断言被削弱                      拒绝晋升

  回归失败                            不晋升正式版本或按策略回滚

  外部应用越权访问风险                权限网关或网络层阻断
  ----------------------------------------------------------------------------

## 12. 首期最小纵向切片

首期推荐：人工 TestCase、人工审核 Oracle、Task/Run、Playwright
执行、Event 持久化、Evidence 保存、基础 Evidence Graph、规则 + LLM
诊断、少量只读 Probe、Disposition 和报告。

首期不要求完整 Agent 自主探索、复杂贝叶斯诊断或自动修复正式资产。
