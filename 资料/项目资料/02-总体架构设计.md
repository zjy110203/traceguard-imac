# TraceGuard 总体架构设计

-   架构基线：v1.1
-   状态：总体架构基线；模块内部接口待详细设计
-   架构风格：模块化单体 + 独立异步 Worker + 隔离浏览器执行环境

## 1. 架构设计原则

1.  业务闭环优先：围绕需求、测试、证据、诊断和质量改进组织。
2.  Agent 与事实分离：Agent
    提出候选信息；确定性模块负责事实、状态和最终判定。
3.  领域边界清晰：每个核心对象具有明确所有者和生命周期。
4.  可信预期优先：Test Verdict 必须依据已批准 Oracle 和确定性规则。
5.  证据可追溯：诊断结论保留支持、反驳和不确定性证据。
6.  最小权限：Agent、Probe、Browser 和 Repair 仅获得必要权限。
7.  先模块化单体：不为架构图完整而提前拆分微服务。
8.  可验证设计：关键能力有契约测试、集成测试和 Benchmark。

Orchestrator 管理 Task 调度。 - Engine 负责具体执行，不由 Agent
自由裁决正式测试结果。

## 4. 子系统 B：证据驱动的故障诊断

``` mermaid
flowchart TD
    A["Execution Events"]
    B["Event Collector"]
    C["Evidence Manager"]
    D["Evidence Correlation Service"]
    E["Evidence Graph"]
    F["Failure Triage"]
    G["Diagnosis Workflow"]
    H["Hypothesis Manager"]
    I["Active Diagnosis Planner"]
    J["Probe Registry / Engine"]
    K["Diagnosis Report"]

    A --> B --> C --> D --> E
    E --> F --> G
    G --> H --> I --> J
    J --> C
    H --> K
```

  模块                           职责
  ------------------------------ ------------------------------
  Event Collector                接收、持久化、幂等处理 Event
  Evidence Manager               管理原始、规范化和派生证据
  Evidence Correlation Service   建立证据关系
  Evidence Graph                 提供证据关系视图
  Failure Triage                 初步分类失败
  Diagnosis Workflow             组织诊断生命周期
  Hypothesis Manager             管理多候选假设
  Active Diagnosis Planner       评估下一步探针
  Probe Registry                 管理探针定义和权限
  Probe Engine                   执行授权探针

关键约束： - 时间接近不等于因果。 - Trace ID / Request ID
关联不自动证明因果。 - Probe 执行失败不等于目标故障成立。 -
证据冲突无法解决时允许 INCONCLUSIVE。 - 多个根因和促成因素可以同时存在。

## 5. 子系统 C：安全修复与持续质量优化

``` mermaid
flowchart TD
    A["Diagnosis"]
    B["Failure Disposition Router"]

    B --> C["Product Defect"]
    B --> D["Test Asset Issue"]
    B --> E["Environment / Data Issue"]
    B --> F["Timing / Flaky"]
    B --> G["Agent / Automation Issue"]
    B --> H["Inconclusive"]

    C --> I["Defect Management"]
    D --> J["Repair Advisor"]
    J --> K["Repair Service"]
    K --> L["Approval Manager"]
    L --> M["Sandbox Validation"]
    M --> N["Regression Manager"]
    N --> O["New TestCaseVersion"]

    F --> P["Flaky Analyzer"]
    E --> Q["Environment / Data Handling"]
    G --> R["Agent Execution Analysis"]
```

处置原则： - 产品缺陷进入缺陷管理。 - 测试资产问题可以进入修复建议。 -
环境和数据问题进入对应处置。 - Timing / Flaky
是不稳定特征，需要继续分析来源。 - Agent / Automation
问题进入自动化链路分析。 - 证据不足时保留不确定性，不强制进入修复。

Repair Advisor 只提出候选修改；Repair Service 管理提案生命周期；Approval
Manager 保存审批记录；正式晋升必须经过策略、沙箱和回归检查。

## 6. Agent Orchestration 支撑体系

-   Agent Registry：Agent 能力、版本和配置登记。
-   Agent Runtime：Agent 执行环境。
-   Workflow Orchestrator：有状态工作流。
-   Context Manager：上下文和记忆范围。
-   Tool Registry：工具描述和输入输出契约。
-   Tool Permission Gateway：工具调用权限。
-   Model Gateway：模型供应商和调用统一入口。
-   Checkpoint & Recovery：工作流检查点和恢复。

Agent 可以提出候选信息，但不能绕过业务模块直接修改权威数据。

## 7. Data & Evidence Infrastructure 支撑体系

  组件                   主要用途
  ---------------------- ----------------------------------
  PostgreSQL             业务状态、关系、任务、事件元数据
  Redis                  Broker、缓存、短期协调
  MinIO / 对象存储       截图、视频、HAR、原始日志附件
  Event Infrastructure   事件持久化、投递和消费
  Schema Registry        契约版本和 Schema
  Audit Log              用户、Agent、工具和管理操作审计

PostgreSQL 是业务状态权威来源。Redis
不作为第二套权威业务数据库。对象存储保存大文件，数据库保存元数据、引用和索引。

## 8. Test Environment & Benchmark 支撑体系

1.  TeamFlow：受控业务应用，提供业务状态、API、日志和故障注入。
2.  External Web Apps：外部真实应用，用于探索、执行和有限泛化验证。
3.  UI-FaultBench：数据集、Ground Truth、实验运行、指标和报告。

外部应用没有独立可信 Ground Truth 时，不宣称根因诊断准确率。

## 9. Platform & Visualization 支撑体系

建议工作台页面： - 项目工作台； - 测试需求； - 测试资产； - 执行中心； -
证据中心； - 诊断中心； - 修复中心； - Benchmark； - 权限与审计管理。

实时事件通过 SSE 推送。SSE
是展示通道，持久化事件和业务状态才是权威来源。

## 10. 架构风格与部署边界

建议初期采用模块化单体后端、独立 Celery
Worker、独立浏览器执行进程或容器、PostgreSQL、Redis、对象存储和 Vue
前端。

不建议首期拆分大量微服务，也不强制采用图数据库。Evidence Graph
可以先以关系表和查询服务实现，是否引入专用图存储由规模和查询需求决定。

## 11. 关键架构约束

1.  每个业务对象有唯一业务写入责任模块。
2.  模块间通过明确服务接口、命令或事件交互。
3.  Agent 不直接操作数据库。
4.  正式 Test Verdict 由确定性规则产生。
5.  Diagnosis 保留证据和不确定性。
6.  Repair 不得削弱原始 Assertion。
7.  Ground Truth 与被测 Agent 的运行上下文隔离。
8.  外部应用执行环境受到严格网络和权限限制。
