## 1. `src/agentic_explorer/main.py`（入口，750 行）

**关键片段**
- 路由关键词常量：
  ```python
  ADVANCED_KEYWORDS = ("accessibility","a11y","data_heavy","data-heavy",
      "impatient","returning","explorer","chaos","autonomous")  # main.py:43-53
  ```
- 初始状态（`main.py:499-506`）：`messages=[HumanMessage(prompt)]`、`next_agent=""`、`step_count=0`、`action_tape=[]`、`bugs_found=[]`、`explored_paths=[]`。
- 上下文预算：`_bound_transcript_for_report()`（`:68-82`）保留头 6000 字符 + 尾约 28k，中间标注省略量。
- 重试：`max_retries=5`，rate-limit 时 `delay=30+attempt*15+random(0,10)`（`:606`），其余指数退避 `base_delay*(2**attempt)`（`:609`）。
- 报告写入后追加 tape 摘要（`:713-720`）。

**设计模式**：模板方法式主流程；上下文预算（bounded context）；best-effort 记忆写入（`try:...except: pass`，`:694-704`、`:726-733`）。

**值得借鉴**：①LLM 报告 transcript 头尾保留而非简单截断；②stream_mode 双模（`updates`+`messages`）同时拿到状态增量与实时消息；③message-id 去重避免 checkpoint 恢复后 traces 重复。

**疑点与局限**：
- `_is_transient_error()`（`:151-153`）基于**错误字符串匹配**（"503/UNAVAILABLE/429/..."）判断重试，脆弱且与 SDK 异常类型脱钩；`ARCHITECTURE_GUIDE.md:1634-1638` 示例的关键字与此不一致（文档声称）。
- 报告是**LLM 主观叙述**，PASS/FAIL 由 LLM 依据 transcript 判定（`:652-661`），无外部 oracle。
- 多个 `except Exception: pass`（记忆写入）会**静默吞掉失败**，记忆可靠性无保障。
- mission 串行执行 + 固定 cooldown（`:722-724`），无并发。

## 3. `src/agentic_explorer/memory.py`（717 行）

**关键片段**
- 命名空间（`:7-15`）：`("app"|"episodes"|"procedures", url_hash, ...)`，`app_url_hash()`（`:27-30`）去 query/fragment 后 sha256[:12]。
- Bug 指纹：`_bug_fingerprint(summary, page)`（`:254-257`）`md5(f"{page}:{summary[:100]}".lower())[:12]`。
- 程序性记忆：`update_procedural_memory()`（`:495-579`）用 `create_prompt_optimizer(llm, kind="prompt_memory")`，以会话摘要为 trajectories 优化各 agent prompt 与 routing rules，带 `version` 字段。

**设计模式**：Namespace 化 KV 记忆；单调递增计数器（visit_count/seen_count/confirmed_count）；langmem 反思闭环；语义检索失败回退关键词（`_semantic_search()` `:170-177`、`get_recall_tool()` 内 `_search` `:337-347`）。

**值得借鉴**：①把 selector 成功率、页面风险评分做成可查询记忆并注入 supervisor；②"程序性记忆"用 prompt optimizer 沉淀经验而非硬编码。

**疑点与局限**：
- `except (TypeError, Exception)`（`:175,341`）写法冗余——`Exception` 已覆盖 `TypeError`，实际是**捕获一切**，可能掩盖真正的 store 错误。
- `update_procedural_memory()` 以 **thread_id 当作 agent_name** 建立 prompt 记忆（`:528-533`：`agent_names.add(s.value.get("thread_id",""))`），与按角色（如 `new_user_agent`）优化的意图不符——每次 mission 的 thread_id 不同，会产生大量按 thread 的条目，疑为设计偏差【源码推断】。
- Bug Catalog 的 page 来自 `reversed(explored_paths)` 取最后一个非空路径（`write_episode_memory()` `:316-322`），是**近似定位**，非 bug 的真实发生页面。
- 记忆写操作多为 best-effort，无事务保证。

## 4. `src/agentic_explorer/orchestration/graph_base.py`（656 行，核心）

**关键片段**
- `AgentState`（`:70-80`）：
  ```python
  class AgentState(TypedDict):
      messages: Annotated[Sequence[BaseMessage], operator.add]
      next_agent: str
      action_tape: Annotated[List[Dict[str, Any]], _bounded_tape_reducer]
      step_count: Annotated[int, lambda _old, new: new]
      bugs_found: Annotated[List[str], operator.add]
      explored_paths: Annotated[List[str], operator.add]
  ```
- `_sanitize_messages_for_model()`（`:378-401`）：丢弃 `SystemMessage`/`ToolMessage`，历史仅作叙事文本，规避 Anthropic "non-consecutive system / orphaned tool_result" 错误。
- `make_supervisor_node()`（`:468-563`）：`routing_schema` 枚举 `[*agent_names, "FINISH"]`（`:480-488`），`with_structured_output(..., method="function_calling")`（`:489`）。
- `compile_swarm()`（`:630-655`）：`agent → Summarizer → Supervisor → 条件边`，`set_entry_point("Supervisor")`。

**设计模式**：节点工厂（make_*_node 闭包）；自定义 reducer 控制状态增长；结构化输出做路由；消息清洗适配器；图编译集中化。

**值得借鉴**：①`_bounded_tape_reducer` 让 state 只留最近 50 条、全量在磁盘，兼顾上下文与可追溯；②Supervisor 路由简报分段且有界（`_build_routing_context()` `:318-336`），避免长会话撑爆上下文；③`dedupe_bugs` 的标题前缀归一化去重（`:117-156`）。

**疑点与局限**：
- `BROWSER_AGENT_RULES`（`:24-49`）把"缺失 tooltip、无 help 区、无进度指示"等都定义为 bug 并要求"不要遗漏小问题"，会**系统性放大 bug 计数**——更像 UX 建议清单而非缺陷判定，证据可信度存疑。
- `dedupe_bugs` 用 12 字符前缀重叠判断（`:132-143`），可能把不同 bug（共享开头词）误合并或把同一 bug 的不同措辞漏合并。
- `make_agent_node()` 的 `_extract_bugs`/`_extract_paths`（`:461-462`）基于文本正则与 tool_call 参数，非结构化证据。
- 文档中的行号（如 `graph_base.py:442/291/55`）与实际（`:630/468/70`）系统性偏移，**以源码为准**。

## 5. `orchestration/standard_graph.py`（112 行）与 `advanced_graph.py`（140 行）

**关键片段**
- 两图工具装配几乎一致：`filter_base_tools(base_tools)` + `[execute_browser_command, get_dom_snapshot, bug_screenshot, generate_reproduction_spec]`（+ store 时加 recall/memory tool）（`standard_graph.py:57-68`、`advanced_graph.py:65-73`）。
- 角色由 focus 文本定义（`standard_graph.py:70-83`、`advanced_graph.py:77-94`）；explorer 用自定义 prompt（`:106-119`）。
- 关键：`stock PlaywrightBrowserToolkit` 被 `filter_base_tools()`（graph_base.py:93-100）显式剔除，注释说明"agents emit JSON intents only"。

**设计模式**：Builder/工厂函数；共享基础设施 + 差异化 persona 注册表；工具白名单过滤。

**值得借鉴**：角色 = 同一 LLM + 不同 system prompt + 相同工具集，扩展新角色成本低。

**疑点**：
- 两图 builder 代码高度重复（工具装配、agent 构造、图装配），可抽取公共函数；当前重复带来维护漂移风险。
- 所谓 "swarm" 实际无 agent 间直接协作，命名易误解。

## 6. `tools/browser/engine.py`（636 行，核心）

**关键片段**
- `ALLOWED_ACTIONS`（`:253-256`）：11 种动作。
- `_dispatch()`（`:363-408`）：action→Playwright 调用映射；`extract_text` 截断 4000 字符。
- `_validate_selector()`（`:326-335`）+ `_BRITTLE_SELECTOR_PATTERNS`（`:305-314`）：拒绝 XPath/位置型 CSS。
- `_HEALTH_CHECK_JS`（`:259-299`）：扫描 `[role=alert]`、`euiCallOut--danger`、`euiLoadingSpinner` 等错误/加载标志。
- `ExecutionResult.to_tape_entry()`（`:349-360`）：记录 ts/action/params/ok/duration/result/error/page_url/page_title。
- `generate_playwright_spec()`（`:565-611`）：Tape→`.spec.ts`。

**设计模式**：Command 模式（JSON 意图）；Record-and-Translate；Tool Factory（闭包捕获 page/config）；**追加式操作日志**（append-only tape：内存为可变 `List`，`_append_tape()` 以文件追加模式写 JSONL，写盘异常仅 warn；源码未发现哈希链、签名或篡改检测，源码注释中的 "immutable" 属设计意图表述，**不构成安全意义上的不可变证据**）。

**值得借鉴**：①Brain/Hands 分离是防"不可复现"的关键工程手段；②selector 韧性守卫把稳定性前移到工具边界；③DOM 快照优先用 Accessibility Tree（更贴近用户可感知内容且天然去噪）。

**疑点与局限**：
- `_DOM_SNAPSHOT_JS` 的 `cssPath()`（`:93-110`）**自己生成了含 `:nth-of-type` 的 selector**，而 `_validate_selector()` 又拒绝 `:nth-of-type`——LLM 若照抄快照里的 selector 会被守卫拒绝，存在内部矛盾【源码】。
- `_HEALTH_CHECK_JS` 的错误选择器含 `euiCallOut--danger`、`euiLoadingSpinner` 等 **Elastic UI 专有类名**，与项目"product-agnostic"定位冲突，对其他前端框架覆盖不足。
- `.spec.ts` 是线性回放，`snapshot`/`check_page_health` 为 no-op，唯一断言是 `extract_text` 长度>0；无"bug 是否重现"的验证，所谓 "100%-reproducible"（docstring `:620-621`）言过其实。
- `_append_tape` 写盘异常仅 warn（`:63-64`），崩溃时可能丢日志；`_ACTION_TAPES` 为进程内全局 dict，多进程/并发 mission 不安全。

## 11. 优点 / 缺陷 / 局限综合分析

### 优点
1. **架构清晰、关注点分离**：Brain/Hands 分离（JSON 意图 + 确定性引擎）、编排/执行/记忆/UI 分层明确（`engine.py` docstring、`graph_base.py`、`memory.py`）。
2. **可复现性工程化**：Action Tape 全量落盘 + Tape→spec.ts 翻译，把"非确定性 Agent 交互"转化为"可重放脚本"（`engine.py:565-611`）。
3. **上下文与状态治理成熟**：有界 reducer、路由简报分段裁剪、Summarizer 压缩、报告头尾保留（`graph_base.py:64-67,318-336,574-623`、`main.py:68-82`）。
4. **稳定性工程**：暂态错误重试与退避、selector 韧性守卫、MCP 优雅降级、消息清洗适配多供应商（`main.py:151-158,508-617`、`engine.py:305-335`、`graph_base.py:378-401`）。
5. **跨会话学习**：三级记忆 + langmem 反思 + 风险排序 + 回归任务生成（`memory.py`）。
6. **安全边界**：Skill 脚本子进程执行 + 目录逃逸防护 + 超时/输出限流（`custom_tools.py:242-344`）。
7. **测试保护核心逻辑**：bug 抽取、spec 生成、上下文裁剪均有针对性单测。

### 缺陷
1. **无独立 Oracle**：bug 判定与 PASS/FAIL 完全由 LLM 自我叙述（`graph_base.py:24-49`、`main.py:652-661`）；`check_page_health`/`analyze_visual_state` 是启发式或未接线，不满足"Oracle 独立于 Agent"。
2. **"复现"名不副实**：spec 是线性回放，无 bug 重现断言，`snapshot`/`check_page_health` 回放为 no-op（`engine.py:558-561`）。
3. **内部不一致**：快照生成的 selector 含 `:nth-of-type` 却被 selector 守卫拒绝（`engine.py:93-110` vs `:305-335`）；`_HEALTH_CHECK_JS` 硬编码 Elastic UI 类名与 product-agnostic 定位冲突。
4. **记忆实现疑点**：`except (TypeError, Exception)` 过度捕获（`memory.py:175,341`）；按 thread_id 而非角色做 prompt 优化（`memory.py:528-533`）；Bug 定位取最后探索路径近似（`memory.py:316-322`）；记忆写入静默失败（`main.py:694-704,726-733`）。
5. **文档与源码脱节**：架构文档标注行号系统性过时，持久化文件名、重试关键字与源码不符（`ARCHITECTURE_GUIDE.md` vs `main.py`）。

### 局限
1. **单人维护**：author=maintainer 一人（`pyproject.toml:8-13`），bus factor 高；浅克隆无法评估长期活跃度。
2. **工程成熟度中等**：无端到端集成测试、无 CI 配置迹象（仓库根目录未见 `.github/`）、全局进程内 tape/state 不支持分布式与并发。
3. **证据可信度边界**：bug 计数的判定标准宽泛（把 UX 建议也算 bug）、去重靠字符串启发式，输出更偏"探索报告"而非"可信缺陷证据"。
4. **适用范围**：面向 UI 探索的启发式检查（错误 banner、spinner、AX 树），对深色模式/复杂 canvas/非标准组件/REST/API 层无覆盖；视觉验证依赖外部 LLM 且未启用。
5. **安全边界**：MCP/skill 来自用户本地配置与脚本，能力强大（可执行任意脚本）；虽防目录逃逸，但**脚本内容本身的可信度完全由用户负责**；`ignore_https_errors=True`（`main.py:442-444`）在测试环境可接受但对生产目标有风险。

### 与 TraceGuard 原则的对照结论
- ATE 符合"Agent 是能力层""Playwright 负责确定性执行"两条；
- **不符合**"Oracle 独立于 Agent"与"相关不等于因果"（其 bug 记录是文本抽取 + 计数，无因果校验）；
- 可作为 TraceGuard 的**编排/执行/复现工程参考**，但其"发现-判定"链路正是 TraceGuard 用 Trusted Oracle + Evidence Graph + Diagnosis 要补齐的短板。
