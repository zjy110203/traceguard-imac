## 4. 需要详细设计的事项

-   Primary Oracle 与 Supporting Oracle 的 Assertion 级规则；
-   多来源冲突裁决；
-   一致性等待窗口；
-   需求来源快照；
-   Oracle 版本不可变策略；
-   Oracle 不可用时的 Assertion 状态；
-   外部应用缺少业务状态接口时的降级策略。

### 4.2 TestCase Compiler

-   Exploration Trace 结构；
-   Action 规范化；
-   Locator 稳定性评分；
-   Assertion 构造规则；
-   测试数据和清理策略；
-   回放次数与晋升条件；
-   人工审核流程。

### 4.3 Execution

-   重试策略；
-   取消与超时；
-   浏览器隔离；
-   任务幂等；
-   Run 终态聚合。

### 4.4 Event

-   Outbox 边界；

-   序号和幂等键规则；
-   重试、死信和重放；
-   消费端幂等；

### 4.5 Evidence Graph

-   派生证据；
-   证据完整性；

### 4.6 Diagnosis / Probe

## 5. 设计风险清单

  风险                        影响                   建议控制
  --------------------------- ---------------------- ------------------------
  Oracle 来源不清             测试结论不可信         预期来源和审批先行
  Agent 直接修改事实          状态和结论不可审计     通过业务服务和权限网关
  Event 丢失或重复            证据不完整或重复       持久化、幂等、重放
  证据相关被误判因果          诊断结论错误           关系类型和来源约束
  Probe 越权或有副作用        数据和环境风险         权限、预算、只读优先
  诊断只输出单一根因          掩盖复杂故障           多假设、多根因
  Repair 削弱断言             假通过                 Assertion Preservation
  Benchmark 数据泄漏          实验结果虚高           按故障机制和场景隔离
  外部应用缺少 Ground Truth   根因准确率无法验证     限制结论范围
  首期范围过大                集成困难、交付不完整   先完成最小纵向切片

## 6. 首期最小纵向切片准入清单

-   [ ] TeamFlow 创建项目流程可稳定运行。
-   [ ] 有独立业务状态查询能力。
-   [ ] TestCase 可人工编写和审核。
-   [ ] OracleSpec 可人工定义和批准。
-   [ ] Task、Run、Step 状态有明确所有者。
-   [ ] Playwright 可确定性执行。
-   [ ] Event 可持久化并幂等消费。
-   [ ] Evidence 可保存原始来源和附件。
-   [ ] Evidence Graph 至少支持基础结构与关联关系。
-   [ ] Diagnosis 能输出证据和不确定性。
-   [ ] Probe 具有权限和只读限制。
-   [ ] Disposition 能区分产品、测试、环境和不确定情况。
-   [ ] 报告能追溯 TestCase、Oracle、Run、Evidence 和 Diagnosis。
-   [ ] 安全和隐私基本控制通过验证。

## 7. 设计冻结原则

1.  总体架构不因局部模块偏好频繁变化。
2.  新增模块必须说明现有模块为何不能承担。
3.  新增字段必须说明生产者、消费者和语义。
4.  新增状态必须说明状态转换和终态。
5.  新增 Agent 能力必须说明工具权限和确定性边界。
6.  新增诊断结论必须说明证据和确认规则。
7.  任何修复不得绕过 Oracle 和 Assertion 保护。
8.  任何评测指标必须定义分子、分母和排除条件。
9.  未经评审的建议不得标记为已冻结。
10. 设计变更必须记录影响的文档、契约和测试。
