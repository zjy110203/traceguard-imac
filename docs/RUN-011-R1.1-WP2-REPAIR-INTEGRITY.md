## 1. 服务端血缘校验（`RepairService.propose()`）

写库前按顺序完成，任一失败即拒绝且**不产生提案**（用例统一断言 `len(svc.list())` 不变）：

1. `base_version` 必须对应真实 TestCaseVersion；`changes` 非空；
2. Workspace 一律取版本行权威值；请求 `workspace_id` 不一致 → 403；
3. Diagnosis：存在、kind=`diagnosis`、`testcase_id` 一致、`workspace_id` 一致；
4. Run：存在、Workspace 一致、用例一致、版本与 `base_version` 一致；
5. Diagnosis.run_id 与 source_run_id 一致；只给 Diagnosis 时服务端回填真实 Run；
6. Run 必须终态，结论为 `FAILED` 或带失败证据的 `NOT_EVALUATED`，`PASSED` 一律拒绝；
7. 提案记录写入 `lineage` 快照（diagnosis/run/testcase/version/verdict/status/verified_at）。

## 2. 来源真实性

| 声明 | 服务端行为 |
|---|---|
| 空 / `human:*` | 改写为 `human:{actor}`；actor 来自认证 Principal（API 层）或可信内部调用参数 |
| `rule:<id>` | 必须在 `RULE_SOURCE_CONTRACTS` 白名单；变更路径必须符合结构约束与数量上限 |
| `llm:<model>` | 普通 API 调用方一律 403；仅 `llm_suggest()` 中 Advisor 真实成功返回（`called and not fallback`）才允许 |
| `created_by` | API 层由 `trusted_actor()` 从 Principal 取得；客户端声明只写入审计的 `declared_actor_ignored` |

`llm_suggest()` 的 Fallback 路径写 `rule:llm-repair-fallback`，不冒充 LLM。

## 4. 既有安全门禁未弱化

- Diff Allowlist / Assertion Preservation / Oracle Integrity 仍在 `propose()` 中执行；
- Sandbox 仍由独立 Worker 真实执行；人工审批、CAS 晋升、回归、回滚、幂等回执均未修改；
- PROBABLE 诊断可产生候选，但 `outcome` 与 `disposition` 保持不确定，不会升级为 CONFIRMED。
