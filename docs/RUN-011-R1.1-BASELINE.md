## 1. 为什么 TestCase 属于 `ws-run011-r1-1`，Probe Budget 却是 `default`？

### 1.1 源码链路（逐跳）

1. **TestCase 的 Workspace 是正确的。**
   `POST /api/v1/testcases` 把请求体 `workspace_id` 传给 `CatalogService.create_testcase()`，
   行级 `tg_testcase.workspace_id` / `tg_testcase_version.workspace_id` 均写入该值
   （`packages/persistence/traceguard_persistence/catalog.py:203-266`；路由 `routers/catalog.py:128-172`）。
   编译路径同样把 Intent 的 Workspace 带进候选用例
   （`apps/api/traceguard_api/services/exploration_service.py:271`）。

2. **Task 创建丢失了 Workspace。**
   `TaskService.create_task()` 的签名是：

   ```python
   def create_task(self, testcase_ref, idempotency_key, application="teamflow", *,
                   testcase_version_id="", mode="playwright", workspace_id: str = "default")
   ```

   （`packages/execution/traceguard_execution/tasks/service.py:95-104`）
   路由 `POST /api/v1/tasks`（`routers/execution.py:76-92`）与
   `POST /api/v1/testcases/{testcase_id}/execute`（`routers/execution.py:144-170`）
   **都不传 `workspace_id`**，因此全部落到 `"default"`，并写入 `tg_task.workspace_id`
   （`models.py:105` 列默认值同样是 `default`）。

3. **Run 忠实继承了错误的 Task Workspace。**
   `create_run()` 用 `task.workspace_id` 写 `RunRow.workspace_id`
   （`tasks/service.py:206-218`），于是正式 Run、失败 Run 全部是 `default`。

4. **Probe 忠实继承了错误的 Run Workspace。**
   `plan_and_probe()` 取 `run.get("workspace_id") or "default"`
   （`probe_service.py:356`），`budget_for()` 用该值建立预算文档
   （`probe_service.py:168-179`），`_save_budget_doc()` 把它写进 `tg_doc.workspace_id`
   （`probe_service.py:155-166`）。因此预算文档记为 `default`。

5. **证据文档同时记录了两个互相矛盾的 Workspace。**
   探针证据 `content.workspace_id` 写的是调用参数，而 `tg_evidence.workspace_id`
   也是同一值（`probe_service.py:229-264`）。所以"TestCase 在 A、证据在 default"
   在数据库里是自洽的——只是**业务链断开了**。这正是上一轮没有发现的原因。

### 1.2 实物证据

`docs/assets/run011-r1/lineage/loop1.json`：

- `workspace`（本轮声明）= `ws-run011-r1-1`
- `phases.probe.budget.workspace_id` = `default`
- `phases.probe.budget.scope_key` = `diagnosis:diagnosis_1795576502919eff4037ad9cc`
- `phases.probe.budget.owner_run_id` = `run_17955764721925f11e3fce7b6`

而 `loop1-db.json` 的 17 项检查中**没有一项**检查 `tg_task/tg_run/tg_probe_budget` 的
`workspace_id` 是否等于 `ws-run011-r1-1`。

### 1.3 实际影响

- Workspace 隔离在"执行与证据"这一整段链路上是**名义隔离**：A 空间的 Run、Evidence、
  Probe、Repair 会落到 `default`，任何只能看 `default` 的用户都能读到它们。
- 反向也成立：`default` 空间的用户执行用例时，产物会混进 `default`，无法按空间统计与清理。
- 由于 `tg_doc`（diagnosis/probe_plan/probe_execution/repair/graph）都带 `workspace_id`，
  一旦上层按 Workspace 过滤，业务链会出现"Run 在 default、Diagnosis 在 default、
  但 TestCase 在 A"的跨空间引用。

### 1.4 修复方案（本轮实施）

- `TaskService.create_task()` 的 `workspace_id` 改为**必填**（`None` 即 fail-closed，
  抛 `WORKSPACE_REQUIRED`），删除 `"default"` 默认值；全部内部调用点显式传值。
- 新增服务端解析函数 `resolve_testcase_workspace(testcase_id, version)`：
  从 `tg_testcase_version` 行读取权威 Workspace，**忽略请求体声明**。
- `POST /tasks` 与 `POST /testcases/{id}/execute`：先解析版本与 Workspace，
  再用 `Principal` 校验访问权，最后创建 Task。
- `create_run()` 增加数据库归属校验（见 §3）。
- `RepairService.sandbox_run()` 显式传 `workspace_id=doc["workspace_id"]`。
- `ProbeService` 的预算/执行/计划一律从 Run/Diagnosis 行反查 Workspace，
  不再采信请求体。

## 2. 认证中间件的能力边界（为什么"有 403"不等于"有隔离"）

`auth_middleware()` 目前只做三件事（`apps/api/traceguard_api/auth.py:258-322`）：

1. Token → `Principal`（未认证 401）；
2. CSRF 校验；
3. `action_for_request()` 路径级 RBAC + **query 参数** `workspace_id` 的白名单校验
   （`resolve_workspace_scope()`，`auth.py:105-118`）。

由此产生的绕过面：

| 绕过方式 | 例子 | 结果 |
|---|---|---|
| 路径参数带他人对象 ID | `GET /api/v1/runs/{B_run}` | 200 + 完整报告 |
| body 声明 workspace | `POST /intents {"workspace_id": "B"}` | 直接写入 B |
| 不传 workspace | `GET /api/v1/tasks` | 返回全库 |
| query 与对象不一致 | `GET /runs/{B_run}?workspace_id=A` | query 校验通过，实体未校验 |

`require_workspace_doc()`（`auth.py:121-130`）已经存在，但**没有任何路由调用它**
（全仓 grep 仅命中定义本身与文档）。这就是"授权工具存在、但没有接线"。

### 修复方案

- 新增 `apps/api/traceguard_api/workspace.py`，统一出口：
  - `principal_of(request)`：认证关闭时返回 `None`（dev 模式不改变既有行为），
    认证开启时返回真实 `Principal`；
  - `require_entity_workspace(principal, ws, ...)`：对象级 403 `WORKSPACE_FORBIDDEN`；
  - `scope_filter(principal, requested)`：列表作用域（`None` = 全部，`[]` = 无权限）。
- 所有 detail / 写操作路由在**取到实体后**调用同一函数，不各写一套。
- 所有列表路由把作用域下推到存储层（`workspace_ids in (...)`），而非先全查再过滤。

## 3. Run 的版本归属校验缺失

`create_run(task_id, testcase_version_id)` 当前行为（`tasks/service.py:186-227`）：

- 只查 Task 是否存在；
- `testcase_version_id` 为空时回退为 `task.testcase_version_id`；
- **不查该版本是否存在、是否属于 `task.testcase_ref`、Workspace 是否一致**。

因此可以构造"Task 属于用例 A / Run 指向用例 B 的版本"的跨用例执行，
甚至指向不存在的版本字符串（上一轮单测里的 `tcase_x:v1` 就是这个形态）。

### 修复方案

`create_run()` 内增加同事务校验：

1. 解析 `testcase_version_id` → `(testcase_id, version)`，格式非法直接 422；
2. 查 `tg_testcase_version` 行：不存在 → 404；
3. `version_row.testcase_id == task.testcase_ref`，否则 409 `TESTCASE_VERSION_MISMATCH`；
4. `version_row.workspace_id == task.workspace_id`，否则 403 `CROSS_WORKSPACE_RUN`；
5. 可选 `expected_version` 参数用于回归/回滚场景锁定精确版本。

## 4. Repair 血缘：现在已经"写进去"，但还没有"被证明"

`RepairService.propose()`（`repair_service.py:41-120`）目前：

```python
base = self.rt.catalog.get_version(testcase_id, base_version)   # 只有这一处数据库读取
...
"workspace_id": workspace_id or self._workspace_of(base),
"diagnosis_id": diagnosis_id or None,      # 原样落库
"source_run_id": source_run_id or None,    # 原样落库
"created_by": created_by,                  # 来自服务层参数（路由取请求体）
"repair_source": repair_source or "",      # 仅校验前缀
```

缺失的校验（逐条对照指令 §3.1）：

| 指令要求 | 现状 |
|---|---|
| Diagnosis 必须真实存在 | ❌ 未查 |
| Diagnosis.kind 必须正确 | ❌ 未查 |
| Diagnosis.testcase_id == 请求 testcase_id | ❌ 未查 |
| Diagnosis.run_id == source_run_id | ❌ 未查 |
| Diagnosis.workspace_id == TestCase Workspace | ❌ 未查 |
| Run 必须真实存在 | ❌ 未查 |
| Run 必须属于同一 TestCase | ❌ 未查 |
| Run.testcase_version_id == base_version | ❌ 未查 |
| Run.workspace_id == TestCase.workspace_id | ❌ 未查 |
| Run 必须具备真实失败/NOT_EVALUATED 证据 | ❌ 未查 |
| PASSED Run 不得伪装为失败来源 | ❌ 未查 |

`repair_source` 的问题同样明确：`repair_service.py:68-72` 只判断字符串前缀，
`routers/intelligence.py:353-364` 把客户端 `repair_source` 原样透传，
因此任何调用方都能自称 `llm:gpt-5`。`created_by` 来自 `RepairProposeReq.created_by`
默认值 `agent:repair-planner`，与真实发起人无关。

### 修复方案

1. 新增 `RepairProvenance`（服务端解析结果）：`actor` / `source` / `verified`。
2. `propose()` 在写库前完成 §3.1 的全部校验；只给 diagnosis 时自动回填
   `source_run_id = diagnosis.run_id`。
3. 失败来源判定：Run 必须终态，且
   - `test_verdict == FAILED`，或
   - `test_verdict == NOT_EVALUATED` 且报告存在失败步骤/未评估断言，
   并且 `test_verdict != PASSED`。
4. `repair_source` 规则：
   - API 通用入口：`human:*` / 空 → 服务端改写为 `human:{principal.actor_id}`；
     `rule:<id>` 仅接受白名单规则且变更路径必须符合该规则的结构约束；
     `llm:*` 一律 403（只能由内部 Advisor 成功路径写入）。
   - `llm_suggest(propose=True)`：只有 `advice.called and not advice.fallback`
     才写 `llm:<model>`。
5. `created_by` 只来自 `trusted_actor()`（认证开启时即 Principal；关闭时保留显式声明并标
   `created_by_source=declared_dev`）。

## 6. DB 复核脚本的缺口

`scripts/verify_db_run011.py` 的 Workspace 相关检查只有：

- `workspace_counts`：统计各表在该 Workspace 下的行数（`:250-263`）；
- `lease_owner` 分布、Run verdict 分布（均按 `:ws` 过滤）。

没有"逐 ID"检查。于是：

- `tg_task.workspace_id` 与 `tg_testcase.workspace_id` 不一致不会被发现；
- `tg_run.workspace_id` 与 Task 不一致不会被发现；
- `tg_doc`（diagnosis/probe/repair）的 `workspace_id` 不一致不会被发现；
- Sandbox 三件套（TestCase/Task/Run）不一致不会被发现。

### 修复方案

新增 `workspace_lineage` 检查族：对主链每个实体输出
`id / workspace_id / parent_id / testcase_id / version_id / run_id / diagnosis_id / proposal_id`，
任一不等于目标 Workspace 或父实体 Workspace → 直接 FAIL。

并且负向用例必须验证"数据库没有产生非法写入"，而不只是 HTTP 403。
