## 三、R2：Browser Use、Stagehand 专项

**研究目标**：为阶段 5 Explorer Agent 的浏览器探索与"AI+确定性"结合提供源码级依据。

**研究内容**：
- Browser Use：REPL+CDP 执行循环、页面观察、动作生成、judge 结构化输出、错误恢复、工具机制、1.0 架构（model+REPL+CDP）
- Stagehand：act()/observe()/extract() 三 API 源码实现、Action 结构与零推理重放、selector/locator 策略、accessibility tree 处理、缓存机制
- 二者对比：Agent 交互模式、浏览器控制抽象、页面观察方法、动作生成、错误恢复、对 Explorer 的适用性

**交付标准**：
- 两项目各 5～6 份源码研究文档
- 一份二者对比报告（明确对 Explorer 的建议）
- 标注版本号与架构差异（Browser Use 1.0、Stagehand v4）

**开发关系**：阶段 5 Explorer；P02（Browser Use/Playwright 集成方式）PoC 输入；不预设可共享浏览器上下文。
**顺序提示**：R2 先完成 Browser Use/Stagehand 的源码与架构研究；但**正式开展 P02 集成 PoC 之前，应先完成 R3 中 Playwright 的必要 API 与浏览器生命周期研究**（Browser/Context/Page、Locator、会话隔离、Trace）。不因 R2 编号在前就在未掌握 Playwright 集成边界时得出"可共享浏览器上下文"的结论。

## 四、R3：Playwright、pytest 专项

**研究目标**：确定哪些能力直接建立在框架之上，哪些由 TraceGuard 自研，避免重复实现。

**研究内容**：
- Playwright：Browser/Context/Page/Locator 实现、自动等待机制、网络监听、Trace 录制格式、Test Runner 并行/重试、Trace Viewer 数据模型
- pytest：Fixture/Scope 机制、Hook 系统、Plugin 加载、参数化、测试生命周期
- 边界判定：TraceGuard 应直接复用（执行、断言重试、Trace 录制）vs 自建（Oracle、Verdict、Evidence、Diagnosis）

**交付标准**：
- 关键机制源码笔记（定位到文件/函数）
- "直接建立 vs 自研"能力清单（含理由）
- P01 版本锁定与兼容矩阵建议（基于官方兼容资料与 PoC）

**开发关系**：阶段 2 执行内核；阶段 0 依赖锁定。

## 五、R4：ReportPortal、Allure、OpenTelemetry、Langfuse 专项

**研究目标**：厘清 LLM Agent Trace、应用运行 Event、Testing Evidence 三者的数据模型差异与关联。

**研究内容**：
- ReportPortal：Launch/Test Item 数据模型、失败分类、历史分析、Automatic Analysis、Quality Gate（付费边界）
- Allure：结果数据文件结构、TestCase 身份、Attachment、历史/重试
- OpenTelemetry：① Specification（Trace/Span/Event/Context/Resource 规范、语义约定）；② **Python SDK**（后端 FastAPI 埋点：`opentelemetry-python`）；③ **JavaScript/前端 SDK**（Vue3 浏览器侧采集：`opentelemetry-js`）；④ **Collector**（`opentelemetry-collector`，是否引入的评估）。注：本轮仅核实了 Specification 规范仓库（L3 规范级），SDK 实现仓库尚未做官方核实——规范仓库不足以支撑 SDK 集成，R4 需补齐。
- 关联问题：Python 后端如何埋点、Vue 前端如何采集、是否需要 Collector、OTel Trace 如何与 TraceGuard Evidence 关联（禁止把 OTel Span 直接当正式 Evidence）。
- Langfuse：LLM 语义 trace、Dataset/Experiments、EE 许可边界
- 三者对照：LLM Trace（Langfuse）vs 应用 Event（OTel）vs Testing Evidence（TraceGuard 自建）的字段、可信边界、关联方式

**交付标准**：
- 四者数据模型对照表
- "三类数据不可混同"边界报告
- OTel Python/JS SDK 与 Collector 集成评估（后端埋点、前端采集、Context 传播、Evidence 关联、是否引入 Collector）
- 报告层自建 vs 引入论证（满足项目资料/10 第 7 章「设计冻结原则」第 2 条）

**开发关系**：阶段 3/4/7/13；阶段 4 Event/Evidence 字段设计。

## 六、R5：Healenium、LangGraph、Inspect AI、Neo4j 专项

**研究目标**：支撑自愈、工作流、评测、图存储的详细设计与待确认项。

**研究内容**：
- Healenium：候选定位器算法（LSC 若能获取）、成功 locator 基线、反馈闭环
- LangGraph：Checkpoint 后端（PostgresSaver/SqliteSaver）、human-in-the-loop 中断恢复、节点重试语义、子图
- Inspect AI：Task/Dataset/Solver/Scorer、200+ 评测、Log Viewer、工具型 solver
- Neo4j：属性图建模、Cypher 多跳、GDS；结合 TraceGuard 数据规模评估 P12

**交付标准**：
- 四项目机制级研究笔记
- LangGraph Checkpoint vs PostgreSQL 权威边界说明
- P05（EIG 权重）、P12（图数据库必要性）的评估输入

**开发关系**：阶段 6/8/9/10/11；阶段 10 CAS 晋升；阶段 8 图存储决策。

## 七、R6：BrowserGym、AgentLab、Juice Shop、ZAP 专项

**研究目标**：支撑 Benchmark 环境、外部泛化与安全测试，明确安全测试与 UI 测试边界。

**研究内容**：
- BrowserGym：AbstractBrowserTask、Episode/Reward、Action Space、Observation（补核实）、多 benchmark 任务定义
- AgentLab：Study/ExpConfig、Ray 并行、复现日志、AgentXray、并行限制
- Juice Shop：可控场景与数据自愈、Docker 隔离、场景组织（补核实）
- ZAP：被动/主动扫描、REST API、Automation Framework、第三方许可
- 安全边界：ZAP 安全扫描 ≠ UI 测试诊断；主动扫描授权要求

**交付标准**：
- Benchmark 环境对照与实验管理报告
- 安全测试与 UI 测试边界报告
- P09（Benchmark 规模/统计）、P10（外部应用选择）的评估输入

**开发关系**：阶段 1/11/12；外部应用验证；安全测试设计。

## 八、批次执行纪律

1. 每批次开始前先确认对应 v1.1 阶段设计未变；不因开源项目改变阶段顺序/模块边界/数据契约。
2. 源码级研究须区分"源码事实/文档声称/推断"；标注版本与 commit。
3. 每个新增项目须在决策台账登记，明确借鉴类型（A/B/C/D）与许可证。
4. "研究完成"不等于"批准采用"；引入须评审。
5. 每批次交付后更新总报告与映射文档，保持一致性。
6. 若官方仓库不可访问或设计版本不明确，记录问题、标记待确认，不猜测、不宣称完成。
